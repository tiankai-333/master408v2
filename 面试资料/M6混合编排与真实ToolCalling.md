# M6 混合编排与真实 Tool Calling

## 1. 改造前的问题

旧工作台并不是“模型调用工具”：

- 前端和后端各维护一套正则，容易出现规则漂移；
- `AiAgentPlannerServiceImpl` 直接执行 SQL 查询，再手工拼出 `tools` 数组写入 `toolCallJson`；
- 日志看起来像 tool call，但模型没有选择工具，也没有生成工具参数；
- `/compose paper` 等自然语言命令可以直接进入事务建卷，缺少写操作确认边界。

这套代码有可复用价值。候选题查询、错题优先、知识图谱兜底、事务建卷和个人任务创建都是真实业务能力，不应重写；需要替换的是它们上面的编排方式和不真实的日志语义。

## 2. 当前方案

采用混合路由，而不是让每个请求都先调用一次分类模型：

1. 显式业务 `intent`：确定性路由，置信度 1.0；
2. 高置信正则和强上下文：确定性路由，不增加模型费用；
3. `free_chat` 或低置信文本：交给模型判断是否调用工具；
4. 首个真实工具 `plan_practice`：模型生成知识点、题数、时长和错题偏好参数，应用执行原有 `AiAgentPlannerService`；
5. 工具只返回 `agentDraft`，用户点击确认后，原有 `/api/student/ai/agent/confirm` 才调用事务建卷。

工具执行采用 Spring AI 2.0 的 `ToolCallback + ToolCallingManager`。项目已有领域编排器并需要记录每轮参数、结果、耗时和错误，因此显式持有最多 4 轮的工具循环；模型只能请求工具，真正的方法调用和权限控制始终在应用侧。

## 3. 改造前后对比

| 维度 | 改造前 | 当前 |
|---|---|---|
| 低置信意图 | 正则 miss 后当普通聊天 | 模型可选择真实工具 |
| 工具参数 | 后端写死/手工拼 JSON | 模型按工具 Schema 生成 |
| 工具执行 | 业务 Service 直调后伪装 tool call | `ToolCallingManager` 执行真实回调 |
| 日志 | 假 `tools` 数组 | 真实工具名、入参、结果、耗时、状态、错误 |
| 写操作安全 | 特定自然语言可直接建卷 | 一律先草案，确认接口才写库 |
| 用户隔离 | 依赖控制器线程上下文 | 每请求创建工具对象并绑定当前 `User`，不共享可变参数 |
| 外部模型依赖 | 普通回答依赖模型 | 确定性路由不依赖模型；工具路由异常退回原聊天路径 |

## 4. 成本、并发和稳定性

- 成本：显式和高置信请求不做额外分类调用；普通低置信聊天用路由结果直接回答，通常仍是一轮模型调用；真实工具通常需要“模型选工具 + 工具结果回传模型”两轮。
- 并发：工具实例是请求级对象，当前用户和草案不会存入单例字段或 ThreadLocal，因此并发请求不会相互污染。
- 参数边界：题数最终仍由旧 Planner 限制为最多 5 道，模型参数不能绕过业务校验。
- 稳定性：工具循环最多 4 轮；模型不支持工具或路由异常时不执行写操作，并切回普通对话。
- 审计：`ai_run_log` 中 `model_name=spring-ai-tool-calling` 的记录才代表真实模型工具调用；确定性 Service 路径明确标记 `realToolCall=false`。

限流、舱壁、429 共享配额和压测仍属于计划中的 M8，当前不能宣称已经解决高并发模型调用。

## 5. 测试

- `AiIntentRouterTest` 验证显式意图优先、高置信规则零模型路由、低置信文本进入模型路径；
- `SpringAiToolOrchestratorTest` 构造模型的真实 `tool_call` 响应，验证应用执行工具、将结果回传模型、产生最终回答并写真实调用日志；
- 自动作业不调用外部模型，保证隔离和可重复。

## 6. 面试参考答案

> 我没有把旧组卷逻辑推倒重做。旧项目的 SQL 候选题筛选、错题优先和事务建卷都是可靠的领域能力，我把它们保留在 Service 层，只替换上层编排。显式 intent 和强上下文走确定性路由，避免每次都增加一次模型分类的费用和延迟；正则无法判断的自由文本才让模型选择 `plan_practice` 工具。模型只负责提出工具名和结构化参数，真正执行、用户绑定、参数上限和日志都由应用控制。练习工具目前只生成草案，用户确认后才允许事务建卷，这样模型误判不会直接产生数据库副作用。
