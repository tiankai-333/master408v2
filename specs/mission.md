# Mission — Master408 v2

本文描述项目目标与原则，不是能力已经全部实现的声明。规则层级和变更程序见
[规范治理](README.md#规范效力与变更)；技术禁止项统一见 [技术边界](tech-stack.md#不得采用)。

## 为什么存在

Master408 v2 是面向计算机考研 408 学习场景的 AI 学习工作台，也是一个用于验证
“如何把概率性大模型能力工程化”的长期项目。

项目不是重新制作一个聊天 Demo，也不是为了堆叠 RAG、Agent、MCP、Multi-Agent 等名词。
它在第一代 Master408 的真实题库、考试、错题、学习记录和管理流程上渐进演进，目标是把
模型能力放进一个可验证、可观测、可回退、可维护的软件系统中。

## 服务对象

### 学生

- 需要完成 408 刷题、错题复习和知识点学习的备考用户；
- 希望获得有证据、可追溯、符合个人学习状态的讲解和练习建议；
- 需要对 AI 建议保持控制，特别是组卷等会改变业务状态的操作。

### 内容与系统维护者

- 维护题库、知识点、Prompt、模型配置和评测数据的管理员；
- 需要知道系统为什么给出某个结果，以及模型、检索或工具在哪一步失败；
- 需要在不破坏既有考试业务的前提下持续升级系统。

### 项目作者与技术评审者

- 项目作者通过它建立可迁移的软件工程能力与求职证据，不限定只能投递 Java 后端或 Agent 岗位；
- Feature 结束须有独立解释、实践及自我考核，功能规模不能代替作者的理解；
- 面试官、协作者和后续维护者能够复现关键实验，区分已有事实、设计选择和未来设想；
- 项目演进应能够回答“为什么这样设计”和“如何证明它有效”，而不只是展示功能截图。

## 产品承诺

Master408 v2 应提供：

1. 可用的题库、考试、错题和学习记录主流程；
2. 基于本地知识与题目证据的 AI 讲解和学习辅助；
3. 用户隔离的对话记忆和学习上下文；
4. 只读规划与有副作用执行分离的 Tool Calling；
5. 对模型、Prompt、检索、工具、延迟、Token、成本和失败的可追踪记录；
6. 在外部模型、Redis 或 Qdrant 部分不可用时具有明确的失败或降级行为；
7. 对重要改造提供固定数据集、基线、指标和可复现验证。

## 工程使命

项目长期围绕一个问题建设：

> 如何把不稳定、昂贵、概率性的模型，约束成稳定、可解释、可验证的软件系统能力？

因此工程优先级依次为：

1. 事实与数据正确；
2. 用户安全和兼容性；
3. 可验证的质量提升；
4. 可观测性、可靠性、延迟与成本；
5. 新框架、新协议和更复杂的 Agent 形态。

## 成功标准

项目成功不以功能数量衡量，而以以下证据衡量：

- v1 是可运行、可复现的 Legacy Baseline，v2 是可对照的 Candidate；
- 数据库中的业务事实、派生状态、检索投影和运行日志具有明确所有权；
- Canonical Question 能保留题干、选项、答案、解析、来源和资源语义；
- RAG 改动可以用 Recall、MRR、nDCG、引用正确率、延迟和成本进行比较；
- 模型与工具失败具有分类、边界、追踪、回退或明确错误；
- 有副作用的操作必须经过身份校验、参数校验和用户确认；
- README、规格、代码、测试和运行证据对系统现状给出一致描述；
- 关键结果可以由其他开发者按照文档重新运行，而不是只存在于一次对话中。

## 非目标

- 不为了展示名词而引入 MCP、微服务、多智能体或动态插件平台；
- 不把 AI 生成内容当作底层业务事实；
- 不在缺少评测时宣称检索、Prompt 或模型“更好”；
- 不以一次性重写替代对遗留系统的兼容迁移；
- 不把真实用户数据、未授权题库或密钥写入公开仓库；
- 不让模型绕过后端权限、事务和用户确认直接执行写操作；
- 不把项目包装成已经达到生产规模，而应明确学习项目的真实边界。

## 核心原则

1. **先事实，后抽象**：先确认真实读写链路和运行数据，再决定目标模型。
2. **先验证，后扩展**：没有基线和验收方法的能力不进入主链路。
3. **先只读，后写入**：模型先搜索、读取和规划；写操作必须确认。
4. **确定性系统约束模型**：权限、参数、状态、预算和事务由后端掌控。
5. **渐进迁移**：每一步可回滚、可对比，不因追求整洁破坏成熟业务。
6. **证据优于叙述**：指标、测试、Trace 和失败样本优先于主观结论。
7. **保持可替换性**：业务层不绑定单一模型厂商、Agent 框架或编码代理。
