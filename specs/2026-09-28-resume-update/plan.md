# Plan — 简历更新与面试证据对齐

## 1. 确认版本与建立事实底稿

- 与用户确认优先投递类型、目标版本/页数、教育任职信息变化；有 JD 则做职责匹配，无 JD 则保持软件工程宽方向。
- 读取三个有效版本及既有用语审查，复用证据台账逐条核对；外部项目材料缺失单列，不搜索无关私人文件。
- 复核 408Master 最新代码、验证记录和 Feature 进度，建立“保留/替换/删除/待确认”清单。

出口：每条候选描述有事实状态与证据；用户确认本轮实际维护的投递版本。

## 2. 更新内容与面试追问

- 先更新详细事实底稿，再精简为岗位版本；保留继承与个人贡献边界。
- 为每个数字补快照与口径；无法支持的指标删除或改为可验证的定性结果。
- 从近期成果中择优替换旧 bullet，不机械叠加篇幅；明确设计成果与运行成果的差别。
- 向用户展示修改前后与理由，确认后更新对应 `body.tex`；同一事实同步核对三个版本。
- 为拟投递核心主张准备至少两级追问，记录待补学点。

出口：内容经用户确认，无未处理的强主张或口径冲突。

## 3. 导出与版面核验

- 沿用既有 TeX 构建方式，缺依赖先报告，不为排版改项目技术栈。
- 按生成当天日期归档新 PDF；使用 PDF 技能渲染检查每页，验证可复制文本、链接与目标页数。
- 核对源文件与 PDF 一致，保留旧版本和历史产物；不把生成 PDF 等同于允许投递。

出口：排版与文本检查通过，有源码到 PDF 的明确对应关系。

## 4. 自我考核与收口

- 逐经历进行讲述、源码/配置定位、条件变化追问；关键指标能够解释统计方式和局限。
- 作者独立完成一个与主要项目主张相关的小实践，不强制访问实习生产系统。
- 对答不清的描述补学复测或降级；记录提示与作者确认，不由代理代答后宣布通过。
- 更新版本治理与 roadmap；仅经技术/内容核验及自我考核的版本标为可投递。
