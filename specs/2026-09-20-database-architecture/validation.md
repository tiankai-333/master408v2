## 1. 只读审计（DB-A）

每次报告记录代码提交、库名、结构版本、采样时间和 SQL 原文；仅输出必要的统计与异常 ID。

| 编号 | 检查 | 对应需求 | 统计口径 |
| --- | --- | --- | --- |
| A-01 | 规模与最近写入 | DB-01、DB-07 | 六张表的总数、有效数、最近创建/更新时间 |
| A-02 | 旧主链完整性 | DB-01、DB-10 | 有效题总数；缺 `info_text_content_id`、悬空 ID、空内容、非 JSON 的数量 |
| A-03 | current 完整性 | DB-05、DB-11 | 按题目计数 0 / 1 / 大于 1 分桶；A-03b 输出多 current 明细 |
| A-04 | 孤儿与版本异常 | DB-05、DB-10 | 六类孤儿/重复计数，含无对应题目的内容、来源、知识点与资源 |
| A-05 | 版本历史 | DB-02、DB-05 | 断号、起始版本、版本总数与最大版本不一致的题目；A-05b 检查 current 是否为最新 |
| A-06 | 内容一致性 | DB-02、DB-03、DB-04 | 按题型统计可选字段缺失；再按样本做规范化人工对照，不比较现有 `source_hash` |
| A-07 | 富文本保真 | DB-04、DB-07 | 图片、代码、表格、公式分层计数 + 20 条人工对照样本 |
| A-08 | 来源独有信息量 | DB-07 | `question_source` 覆盖率与 URL、页码、批次、metadata 的非空数量 |
| A-09 | 删除传播 | DB-08、DB-11 | 已删除题目的 current 内容、RAG 文档、知识点关系与考试引用数量 |
| A-10 | 历史考试 | DB-06、DB-11 | 答题记录的 `question_text_content_id` / `text_content_id` 缺失与悬空数量；A-10b 列出多版本题目 |
| A-11 | RAG 投影 | DB-08、DB-09 | 题目类文档状态分布；A-11b 确认 `source_ref` 语义；A-11c 向量写入状态 |
| A-12 | 并发写入观察 | DB-05 | 在事务中插入重复版本，记录实际错误码后回滚 |
| A-13 | 隔离库约束验证 | DB-05 | 应用候选 DDL 后重复 current 必须被拒绝 |

## 2. 设计验收（DB-C）

每条需求必须有可执行的验证方式。表中的「执行方式」指向具体命令或脚本编号，不是描述。

| 编号 | 需求 | 验证方式 | 目标状态 |
| --- | --- | --- | --- |
| DB-C01 | DB-01 字段所有权 | A-01/A-02 + `data-contract.md` 字段表 | 每个核心字段只有一个目标写入入口；旧入口有迁移或保留说明 |
| DB-C02 | DB-02 版本一致 | A-05/A-05b + `design-test-plan.md` T3 | 读取 API 返回的题干、选项、答案、解析来自同一版本行 |
| DB-C03 | DB-03 题型无损 | T3 五种题型往返 | 选项顺序、项标识、分值与答案语义不变 |
| DB-C04 | DB-04 富文本保真 | A-07 + T3 富文本用例 | 原内容原样保存；派生文本生成可重复；人工对照无语义遗漏 |
| DB-C05 | DB-05 唯一性与并发 | A-03/A-12/A-13 + `ddl/` + T1/T2 | 重复 current 被数据库拒绝；并发编辑有确定结果；事务失败保持原有效版本 |
| DB-C06 | DB-06 历史绑定 | A-10/A-10b + 读取路径走查 + T3 | 创建考试后编辑题库，历史展示与评分使用约定版本；不可恢复项显式报告 |
| DB-C07 | DB-07 关系与来源 | A-04/A-07/A-08 | 新增、修改、回填不丢失人工来源与知识点信息；资源归属清晰 |
| DB-C08 | DB-08 删除语义 | A-09 + T4/T5 | 停用后不再用于新组卷与检索；历史引用仍可读；泄漏范围有处理结论 |
| DB-C09 | DB-09 索引可追踪 | A-11/A-11b/A-11c + T5 | 索引记录源版本与生成配置；失败、重试、重建可观测 |
| DB-C10 | DB-10 迁移可重复 | T4 + 第 4 组隔离库演练 | 同批次运行两次不增加重复数据；中断恢复、冲突隔离、回滚均能对账 |
| DB-C11 | DB-11 管理端契约 | A-03/A-06 + 可承诺/不可承诺清单 | 同一版本在管理端、考试与 RAG 中引用一致；页面字段有服务端定义 |

以上是隔离环境与只读连接的验证场景。只读项可以立即执行；写探针和 DDL 只在隔离库执行。

### DB-M01：两个人同时修改同一道题，后保存的人应该覆盖谁？

面经原型：S1 的数据库乐观锁实现、S2 的乐观锁与悲观锁比较。
项目对应：`QuestionServiceImpl` 的编辑事务调用 `QuestionContentServiceImpl.saveFromEdit`，后者计算新版本、清除 current 并插入内容；对应 DB-05 与 `design-test-plan.md` T2-2。

模拟问句：管理员甲乙同时打开第 3 版题目，甲修改答案并保存，乙随后提交自己修改的解析。你怎样判断乙的提交是否会覆盖甲的答案？请沿实际调用链说明现有行为，再设计冲突处理，而不是只说“加一个锁”。

- 追问：版本号不重复，是否就意味着不会丢失用户修改？如果改用乐观锁或数据库行锁，用户看到的行为和系统代价分别是什么？
- 实践：画出两次请求的 SQL 时序，在隔离环境设计双会话实验，记录事务边界、隔离级别、等待位置、响应和最终内容。
- 考核证据：能解释完整调用链中已有更新语句的锁影响；不能仅凭 `MAX(version) + 1` 就断言一定有竞态。能区分并发提交和用户拿着旧页面提交两种情况。

### DB-M02：保存到一半失败，会留下半道新题吗？

面经原型：S2 的 Spring Boot 事务问题。
项目对应：一次编辑涉及 `t_question`、旧内容与 `question_content`；对应 DB-01、DB-05 与 T2-3。

模拟问句：保存题目时，题目主表和旧内容已经执行更新，新内容插入却抛出异常。你如何证明整次保存会回滚，而不是让题干、选项和答案属于不同版本？请指出事务从哪里开始、在哪里结束。

- 追问：如果异常被捕获后返回“保存失败”，结果会改变吗？如果新增一个写入入口，它是否仍处于同一个事务中？
- 实践：设计一次故障注入，列出失败前后需要对比的记录、current 状态和断言；实现阶段在隔离环境执行。
- 考核证据：能从调用方式、异常处理和事务配置解释结论，不以“方法上有注解”代替验证；明确本地事务覆盖哪些操作。

### DB-M03：题目越积越多，读取当前版本慢了，怎样判断该不该加索引？

面经原型：S1 的 B+ 树索引问题；查询诊断与约束部分为项目延伸。
项目对应：`QuestionContentMapper.xml` 按 `question_id`、`is_current` 查询并按 `version DESC LIMIT 1` 取当前内容；基线含 `(question_id, version)` 唯一索引与 `(question_id, is_current)` 普通索引。

模拟问句：假设题库增长后，读取当前内容的 SQL 成为慢查询。你会收集哪些证据、怎样读执行计划，再决定是否调整索引？请结合过滤、排序和返回字段解释，不能只回答“索引使用 B+ 树”。

- 追问：已有两个索引为什么不能仅凭名字判断哪个更好？若一题有两个 current，`LIMIT 1` 能算修复吗？版本唯一约束和当前版本唯一要求分别约束什么？
- 实践：准备不同题目数、每题版本数的合成样本，对比候选方案的 `EXPLAIN` 和查询结果；另写只读 SQL 检查有效题的 current 数量。
- 考核证据：能区分查询性能与数据正确性，说明索引收益、写入成本及测量条件；没有执行实验时，不宣称性能提升。

### DB-M04：用户超时后又点了一次保存，应该多出一个版本吗？

面经原型：S2 的接口幂等及同一请求识别问题。
项目对应：题目保存新增内容版本，回填存在重复运行场景；对应 DB-05、DB-10 与 T2-1/T2-4。

模拟问句：第一次保存已经提交，但响应在网络中丢失，用户重试；另一个用户则是确实连续编辑了两次。你怎样区分这两种情况，既避免重试制造重复版本，又不吞掉合法修改？

- 追问：如果两次重试同时到达，先查再插是否足够？如果导入任务中断后重新运行，如何定义同一条导入记录？
- 实践：列出顺序重试、并发重试、相同标识不同内容、合法二次编辑四组请求，写出预期响应与数据库记录数量。
- 考核证据：明确请求身份、业务身份和内容相同的区别；能解释去重记录与业务写入的失败边界，而不只是给方案起名“幂等”。

### DB-M05：可重复读能不能让一个月前的考试一直显示旧答案？

面经原型：S1、S2 的事务隔离级别问题；长期考试历史是项目延伸，并非原面经问句。
项目对应：考试引用题目，题目内容与答案存在多处读取路径；对应 DB-01、DB-06、DB-11 与需求表 Q-03。

模拟问句：学生完成考试时答案是 A，一个月后管理员把答案改成 B。学生重新打开历史答卷时，题干、选项、答案和评分依据应该如何确定？有人建议把数据库隔离级别设成可重复读，你如何判断它是否解决了这个需求？

- 追问：创建试卷、开始答题和交卷时分别发生修改，应该在哪个时点固定内容？若旧数据没有保留当时版本，能否用当前答案补齐历史？
- 实践：用一题两版、一次考试画出时间线，列出各时点读取的记录和展示/评分预期，再说明如何验证实际引用链。
- 考核证据：区分事务读取视图和业务长期留存要求；能说明版本引用或快照的取舍，诚实标记不可恢复历史。

### DB-M06：迁移旧题库期间还有人编辑和删除，怎样证明没有漏题？

面经原型：S3 的全量/增量同步、删除处理和同步延迟问题。
项目对应：旧内容到 `question_content` 的回填与新旧读取切换；对应 DB-07、DB-10 与 `migration-plan.md`。

模拟问句：假设迁移不能全程停写，第一次全量回填期间又发生新增、编辑和删除。你怎样安排全量与增量的衔接，证明切换后的内容既不遗漏，也不会让旧内容覆盖新编辑？

- 追问：若用更新时间作为游标，多条记录时间相同或事务较晚提交时怎么办？源端删除的数据如何进入对账？如果允许短暂停写，是否值得简化设计？
- 实践：设计包含新增、更新、删除、同时间戳和中断重试的小数据集，列出批次边界、预期结果、对账指标及停止切换的条件。
- 考核证据：能说明方案成立的前提与失败边界；不把“总条数一致”等同于内容无损，不默认项目必须引入复杂同步基础设施。

### DB-M07：数据库已经更新，向量检索还返回旧答案，谁说了算？

面经原型：S3 的数据库与缓存一致性问题；此处改编为 MySQL 与 Qdrant 的派生索引一致性，不假定二者与 Redis 缓存语义相同。
项目对应：题目内容被用于 RAG，停用与更新需传播；对应 DB-08、DB-09、DB-11 与 T5。

模拟问句：题目第 4 版已在 MySQL 保存，向量更新却失败；恢复时第 5 版更新先完成，第 4 版任务后到。你怎样避免旧任务覆盖新结果，并判断检索返回的内容是否仍然可用？

- 追问：如果题目已经停用，积压任务会不会让它重新出现在检索中？同步一直落后时，用户请求怎样处理，后台怎样发现问题？
- 实践：列出成功、失败、重复、乱序、停用五种事件序列，写明数据库、索引与最终返回结果的预期状态。
- 考核证据：明确权威数据、版本身份、恢复和可观测性；不能只说“最终一致”，需解释不一致期间的用户行为与收敛条件。

### DB-M08：两个批量编辑任务互相等待，怎么查是不是死锁？

面经原型：S1 的死锁及其处理问题。
项目对应：题目编辑跨表写入；批量事务为设计假设，不代表现有系统已发生死锁；关联 DB-05、DB-10。

模拟问句：假设未来两个批量任务在各自事务中按相反顺序修改同两道题，其中一个任务报错回滚。你怎样区分死锁、普通锁等待和慢 SQL，并定位各自持有及等待的资源？

- 追问：统一更新顺序有什么作用，是否足以排除所有死锁？失败后重试整个事务，会不会重复产生版本或外部副作用？
- 实践：在隔离环境用两个会话构造相反更新顺序，记录 SQL 时序、错误及锁诊断证据，再验证选定的调整方案。
- 考核证据：能用证据描述等待关系，解释事务范围、锁顺序和重试边界；不能只给出“重启数据库”或“加分布式锁”。
