# 工作流 — 数据库架构设计（题目领域）

本文件定义**执行节奏**：阶段、门、批次、红线。任务清单仍在 [`plan.md`](../plan.md)；需求与决策立场在
[`requirements.md`](../requirements.md)；验收标准在 [`validation.md`](../validation.md)。

这不是新规则，而是把 plan 的工作规则、requirements 的 D-01..D-12 与 L91 的约束落成可执行的顺序。

## 0. 设计原则（全部继承自现有文档，不新造）

| 原则 | 出处 |
| --- | --- |
| 先事实 → 再决策 → 再契约 → 再物理/生命周期 → 最后迁移设计；顺序不可倒 | plan 第 1–4 组的依赖关系 |
| 每步产出必须是**具名文件**或**可复制的命令结果** | plan 工作规则 1 |
| 写操作**只在隔离库**；共享开发库只跑只读审计 | D-12 |
| **未决策项不先行**；不确定就留在待决策表，不擅自补默认值 | requirements L91；plan 工作规则 3 |
| 阈值（一致率/成功率/覆盖率）由审计基线推导，**不预设数字** | D-11 |
| 结论与真实数据不一致时，**改结论，不改数据** | plan 工作规则 3 |
| 不因本 Feature 批量补外键、删表删列、切换线上读路径 | D-07、范围/非目标 |

## 2. 分工（谁做什么）

| 阶段 | 编码代理 | 作者（人） |
| --- | --- | --- |
| A | 执行只读审计、走查代码、建隔离库、写并跑 T1–T4、写报告 | 提供样本材料（第 43 题）；确认夹具替代方案 |
| B | 把每个待决策做成决策卡（候选 / 代价 / 建议 / 证据指针） | **逐条拍板**，确认写回的决策表 |
| C | 依据审计事实与决策起草字段级契约 | 复核字段所有权与"不可承诺"清单 |
| D | 物理结构附录、隔离库 DDL 与 EXPLAIN 对比 | 接受结构结论；若需扩大范围须先改规格 |
| E | 迁移/对账/回滚设计 + 隔离演练 | **确认回滚动作可接受** |
| F | 逐条核对 validation、同步 technical-debt / roadmap / 事实源清单 | **完成自我考核**并确认结论 |

自我考核不能由代理代劳，这是 `specs/sdd.md` 的规定，也是本 Feature 第 5 组的完成条件之一。

## 4. 四个人工门（不可代劳）

- **G1 决策**：Q-01..Q-07 现在都有事实依据（`audit-report.md` 第 15 节），可以快速拍板；
  Q-09..Q-12 依赖 [`sample-contract.md`](sample-contract.md) 的第 43 题样本。
- **G2 条件门**：不是"必须停下"，而是"技术上失败时必须回退"——若隔离库证明候选约束做不出
  "至多一个 current"，就回到 G1 换方案，不许带着不成立的假设继续写第 4 组。
- **G3 回滚接受**：迁移设计的风险由人接受，不由代理判定。
- **G4 考核结论**：由作者确认，代理只负责记录。

## 5. 版本控制（当前缺口的补救）

**现状（2026-09-21 核对）**：`specs/`、`docs/technical-debt.md`、`docs/数据库事实源清单.md`、
`docs/AI能力路线图.md` 在 `git status` 中显示为**未跟踪**（`??`），`.gitignore` 并未排除它们。

**影响**：SDD 的前提是"规范跨仓库、跨会话长期保留并可追溯"（`specs/sdd.md`）。未入库等于这个前提
不成立——换机器、换代理、回溯"当时为什么这么定"都会断。

**动作**：

- 每个批次结束提交一次，规格与代码同提交；
- commit message 约定：规格 `specs(db): …`、实现 `feat(db): …`、证据 `docs(db): …`；
- **不要因为"还没定稿"就不提交**——未定稿的历史本身就是追溯对象。

## 6. 本次审计暴露、必须进入设计的两个新约束

**① 资源事实在仓库之外（影响 DB-04/DB-12/DB-13、Q-05、Q-12）**

审计证明：题干与解析的**显示事实**是 `apps/frontend/student/public/` 下的外链 HTML——
数据库里只有 `<div class="question-html-ref" data-src="…">` 引用与 `data-fallback` 纯文本投影
（`audit-report.md` 第 8 节）。这些目录的实际规模与状态：

| 目录 | 文件数 | 大小 | git 状态 |
| --- | ---: | ---: | --- |
| `question-html` | 13318 | 159.1 MB | **被 `.gitignore` 排除** |
| `question-assets` | 163 | 20.1 MB | 被排除 |
| `knowledge-html` | 116 | 69.3 MB | 被排除 |
| `knowledge-assets` | 102 | 12.8 MB | 被排除 |

排除原因是授权（`.gitignore` 注释：未授权题库/解析/爬虫知识页，开源仓库只提供原创 Demo Seed）。
因此契约必须显式回答：**外部文件算不算事实源、如何备份与校验、丢失时如何标记"不可恢复"**。
**不得默认它们可以入库**，也不得把"数据库里有一行引用"当作富文本已被保存。

**② 规格未纳入版本控制** —— 见第 5 节。

## 7. 红线（每批次结束复核）

1. `mvn -f apps/backend/backend-app/pom.xml test -Dtest=DatabaseSchemaContractTest` **不得变红**
   —— 共享库结构不得因本 Feature 改动；
2. 共享库（`xzs` / `master408_v2`）**只读**；任何 INSERT/UPDATE/DDL 只在 `master408_design_test`；
3. 报告中的每个数字都能追溯到 A 编号与 SQL 原文；**只有执行过的项才勾选**；
4. 不记录连接口令、账号口令、密钥；
5. 未决策项若被迫先行，必须在产出物顶部写明"违反待决策约束、返工风险高"。

## 8. 可复用性

这套节奏（**事实 → 决策门 → 契约 → 物理/生命周期 → 迁移 → 收敛**）与后续 Feature 无关，
可直接套用到管理端重建、RAG 评测等阶段。稳定一轮之后，建议把第 1–4 节提炼进
`specs/sdd.md`，作为所有 Feature 的默认工作流。
