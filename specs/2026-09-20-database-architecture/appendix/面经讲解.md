## M01 两个人同时改一道题，后保存的覆盖谁？（乐观锁）

**参考答案**

- 乐观锁：读时不加锁，提交时带版本条件更新（`UPDATE ... WHERE version=?`），失败即冲突。适合低冲突、长临界区；无锁等待，代价是冲突后要重试或报错。
- 悲观锁：`SELECT ... FOR UPDATE` 先锁行再改。适合高冲突、短临界区；代价是持锁吞吐下降、有死锁面。
- 关键区分（面试加分点）：**并发提交**（两人同时保存）和**陈旧页面提交**（拿着旧页面覆盖新内容）是两个问题——唯一键/版本重号只解决前者；后者必须让提交携带"打开页面时的版本号"（expectedVersion）做条件更新。

**本项目对照** ▲

- 旧链路：`updateFullQuestion` 同事务 `SELECT MAX(version)+1 → clearCurrent → insert`。
  `(question_id,version)` 唯一键把并发重号暴露为显式 1062（T2-2 实测 `Duplicate entry '990301-2'`）；
  `is_current` 只是普通索引，**不拦**两个不同 version 各自带 `is_current=1` → 多 current，这正是
  D-13 用生成列+唯一索引（候选 A）升级为数据库约束的原因；D-16 的 expectedVersion 防的才是"旧页面覆盖"。
- 剩余竞态的归位：重号→服务层翻译成业务冲突"请刷新后重试"（D-15，不静默重试不返回 500，由用户重试收敛）；
  "必须有 current"→数据库只保"至多一个"（D-14），存在性靠保存事务+业务校验。
- 新库 raw 方向：D-31 砍掉人工编辑，写入=批次导入 → 并发编辑这个形态不存在；同源重复由
  `uk_question_source_ref` 唯一键拦截（1062→批次显式失败），更新=整行替换+新 batch_id，天然无"取号"动作。

**常见追问**

- REPEATABLE READ 能防丢失更新吗？——不能。MVCC 快照读不阻止写写冲突，两个事务都能提交，后者覆盖前者。
- 为什么不用 FOR UPDATE？——编辑页面从打开到提交是分钟级用户操作，持锁不现实；锁只该包住"写"那几毫秒。
- 版本号不重复就等于没丢修改吗？——不等于，重号只是并发提交的一种形态；陈旧页面提交版本号根本不冲突。

## M02 保存到一半失败，会留下半道新题吗？（事务边界）

**参考答案**

- Spring `@Transactional` 默认对 `RuntimeException`/`Error` 回滚，受检异常默认**不**回滚（要 `rollbackFor`）；
- 异常被 catch 吞掉=不回滚，这是最常见的"半提交"来源；
- 传播行为 `REQUIRED` 让多表写共享同一物理事务；同类内部自调用不经代理，事务失效；
- 验证方式是故障注入后对比前后状态，不是"方法上有注解"。

**本项目对照** ▲

- 一次编辑跨 `t_question`、旧 JSON、`question_content` 三处写，必须在同一事务；T2-3 实测失败回滚后原 current 仍在。
- 契约要求（data-contract 7.2）：新写入入口必须与权威内容同事务双写，否则出现"新题干+旧选项"的界面分裂。
- 新库方向：导入管道"校验→确认→提交"每步定义事务边界，批次失败不部分提交。

**常见追问**

- catch 后返回"保存失败"结果会变吗？——会：异常被吞，事务照常提交，半状态落库。
- 事务里能发 HTTP 吗？——不能，外部调用拉长事务持锁时间且无法回滚，必须拆出事务外。

## M03 题多了读得慢，该不该加索引？（索引与 EXPLAIN）

**参考答案**

- 先测量再动手：慢查询日志定位 SQL → `EXPLAIN` 看 `type`（all/index/range/ref）、`key`、`rows`、`Extra`（Using filesort / Using index）；
- 联合索引最左前缀；过滤列放前、排序列随后可消 filesort；区分度低的列（如布尔）单独建索引收益小；
- 索引有写代价与空间代价；区分"查询性能问题"和"数据正确性问题"——后者加索引没用。

**本项目对照** ▲

- `selectCurrentByQuestionId`：`WHERE question_id=? AND is_current=1 ORDER BY version DESC LIMIT 1`。
  现库 6613 题每题恰好 1 个内容行、该查询并不慢——"慢了"要先用数据证明；
- `(question_id,version)` 是唯一索引、`(question_id,is_current)` 是普通索引：名字看不出好坏，行为差异在"拦不拦得住多 current"；
- 一题有两个 current 时 `LIMIT 1` 返回哪行不确定——这是数据完整性异常（审计 SQL 专门查它），不是性能问题。

**常见追问**

- B+ 树为什么适合数据库？——矮胖多叉、叶子链表支持范围扫描，对比 Hash 无序、LSM 写优读劣。
- 最左前缀举个反例？——索引 (a,b) 对 `WHERE b=?` 无效。

## M04 用户超时后重按了一次保存，会多出版本吗？（幂等）

**参考答案**

- 幂等=同一请求执行多次与一次效果相同。识别"同一个请求"分两层：**请求身份**（客户端生成的 token / Idempotency-Key）和**业务身份**（天然唯一键，如订单号、source_ref）；
- "先查再插"有竞态（两个并发重试都查不到），兜底必须靠数据库唯一键；
- 响应丢失的场景，正确动作是**按 ID 重读对账**，而不是盲目重发；
- 要区分：重复请求（幂等吞掉）、合法二次操作（必须放行）、相同身份不同内容（拒绝）。

**本项目对照** ▲

- D-10 明确请求身份与业务身份分立；`SELECT MAX(version)+1` 的竞态靠唯一键暴露而非静默重试；
- 新库导入幂等 = `uk_question_source_ref`（同一来源 URL 重放不产生第二行）；
- 管理端保存的场景答案（architecture-and-cutover §8）：提交成功但响应丢失→前端按钮防重+按 ID 重读，
  依赖"幂等的业务身份判定+冲突响应可区分+requestId 排障"。

**常见追问**

- 两次并发重试同时到达？——唯一键放行一个、另一个吃 DuplicateKey 转业务响应。
- 导入任务中断重跑，同一条记录怎么定义？——业务键（source_ref）+批次记录，重跑零新增（演练实测）。

## M05 可重复读能让一个月前的考试一直显示旧答案吗？（隔离级别 vs 历史一致）

**参考答案**

- 四个隔离级别：读未提交/读已提交/可重复读/串行化；InnoDB 默认 RR，靠 MVCC 实现；
- 关键结论：**RR 的读视图只在事务存续期内有效**。一个月后重开答卷是全新事务，读到的是当前已提交数据——
  隔离级别解决的是"事务内多次读一致"，管不了"跨月历史一致"；
- 历史一致是业务需求，答案是**业务快照/版本绑定**：要么历史记录引用不可变版本行，要么把当时事实存进历史记录本身；
- 旧数据无法恢复当时版本时，显式标记"不可恢复"，不许用当前数据伪装历史。

**本项目对照** ▲

- 旧系统的真实行为：判分结果在提交时固化到作答行（do_right/customer_score）**不随改答案追溯**；
  但重开答卷时题面与"正确答案"读当前数据（绑定可变的 `t_text_content` 行 + `t_question.correct` 列）→ 展示漂移，
  这正是 D-17（历史绑定不可变版本）要修的缺陷；A-10b 实测生产库无多版本样本，D-17 版本绑定从未实现；
- 新库 raw 方向（IA-06）：作答时快照——题面+判分依据+题型分值直接存作答行（不引用当前题行），
  提交判分同一事务写入；证明手段：写入原子性背书 + 无 UPDATE 路径 + 快照指纹巡检 + 合成样本断言
  （提交→改题→回看，断言展示值=快照值≠当前值）。

**常见追问**

- 快照在开始作答时写还是提交时写？——判分依据必须与判分动作同源（提交判分同事务）；进行中作答遇题目替换的
  判定是实施时单独定义的开放点（作者在作答中已如实标注）。
- 怎么防快照被改？——应用层无 UPDATE 路径 + 存 sha256 指纹定期比对。

## M06 迁移期间还有人写，怎么证明没漏？（全量转增量）

**参考答案**

- 经典结构：全量打底 + 增量衔接 + 对账收尾；
- `update_time` 当游标的坑：同一秒批量更新分属多批、事务晚提交导致读到的快照不含已提交数据 → 漏数；
  更稳的游标是 binlog/自增序号；
- 删除传播：源端删除必须进对账（软删标记或墓表），否则目标端永远多数据；
- 对账口径要分栏："本次迁移新增 / 原有 / 跳过未处理"——总条数一致≠内容无损；
- 权衡：允许短暂停写窗口时，方案复杂度断崖下降，不必为小系统引入同步基础设施。

**本项目对照** ▲

- 回填演练（batch5）：分批可执行、重跑零新增（幂等）、软删题不参与、陷阱题（缺 v1 但有 current）
  由**前置普查**发现而非等唯一键报错——直接回填会让整批失败（1062 实测）；
- 口径教训：演练后"20/20 有内容行"掩盖了 1 道被跳过的题，报告必须分三栏；
- 新库方向直接绕开此题：旧库不动、爬虫按契约直写新库，没有"迁移期间双写"问题。

**常见追问**

- 单人项目要不要上 CDC/binlog 同步？——不。维护窗口+停写足够；复杂同步设施的维护成本超过收益。

## M07 库已更新、向量还返回旧答案，谁说了算？（库与派生索引一致）

**参考答案**

- 谁说了算：**权威数据是数据库**，缓存/向量索引都是可重建投影；
- 一致性三件事：失效（更新/删除要传播到投影）、乱序与重复（用版本号或内容指纹判断新旧，旧任务不得覆盖新结果）、
  可观测（对账巡检主动发现失效，而不是等用户报错）；
- "最终一致"必须回答：不一致窗口内用户看到什么、收敛条件是什么、谁来发现不收敛。

**本项目对照** ▲

- 实证存量：A-11 显示 6613 个题目文档全部 `ready`、只有 3774 个有已记录向量，**2839 个（42.9%）ready 但不可检索**；
  另有 40 条 failed 集中在同一分钟的失败批次——"ready≠可检索"不是假想故障，是既有存量；
- 病根：`payload_hash=SHA2(chunk_id|model|collection|vector_id)` **不含正文指纹**——正文变了 hash 不变，
  失效判定恒真；且元数据写入与正文刷新不同事务；
- D-25 的结构修正：展示就绪与检索就绪拆成两个状态，失败不得标为完整成功；
- 新库方向（IA-07）：投影显式携带**源内容摘要**，对账比对"题行摘要 vs 投影携带摘要"，不一致即失效待重建；
  触发在导入管道（按 batch_id 幂等重跑）、发现在对账巡检、**消费者只按就绪状态降级、不负责修复**；
  词法就绪与行同生（FULLTEXT 建在 stem_text 上），向量缺席时 hybrid 单路降级是既有设计。
  ▲（考官观察：`stem_text` 在 v0 可空，display_ready 纪律 2 未覆盖"stem_text 缺失"，实施时应并入上线阀。）

**常见追问**

- 停用的题被积压任务重建出来，会重新出现在检索里吗？——会，所以返回前必须按状态过滤（D-21）；
- 一致窗口内用户体验？——词法单路可用的降级回答，并明确标注"向量检索未就绪"，与"无可用证据"区分。

## M08 两个批量任务互相等，怎么确认是死锁？（锁诊断）

**参考答案**

- 三种"慢"要分开：**死锁**（循环等待，InnoDB 立即牺牲一个回滚，`SHOW ENGINE INNODB STATUS` 看
  LATEST DETECTED DEADLOCK 的持有/等待资源）、**锁等待**（等别人提交，查 `innodb_lock_waits`/`data_locks`）、
  **慢 SQL**（执行本身慢，慢查询日志+EXPLAIN）；
- 预防：固定加锁顺序（全系统按同一顺序访问资源）、事务尽量小、WHERE 走索引避免锁升级为范围；
- 死锁发生：牺牲方重试整个事务——重试前确认事务无不可重复的外部副作用。

**本项目对照**

- 构造：两个批量任务按相反顺序更新同两道题（题 A→题 B vs 题 B→题 A）；统一按题目 id 升序即可消除该形态；
- 旧库批量编辑入口无事务保护（entry-inventory 第 5 节技术债），新库导入管道要求批次事务+固定顺序写入。

**常见追问**

- 固定加锁顺序能排除所有死锁吗？——不能排除全部（多资源交叉仍可能），但能消除绝大多数工程常见形态。

## 附加 A：current 完整性审计 SQL（实践题参考答案）

作者 2026-10-20 的作答即标准答案（考官已核对口径与写法，参考声明如实）：

```sql
SELECT q.id,
       COUNT(qc.id) AS current_rows,
       CASE WHEN COUNT(qc.id) = 0 THEN 'no_current'
            ELSE 'multi_current' END AS anomaly,
       GROUP_CONCAT(qc.id ORDER BY qc.id) AS current_content_ids
FROM t_question q
LEFT JOIN question_content qc
       ON qc.question_id = q.id
      AND qc.is_current = b'1'
WHERE q.deleted = b'0'
GROUP BY q.id
HAVING COUNT(qc.id) <> 1
ORDER BY anomaly, q.id;
```

口径四点：①"有效"只排软删 `deleted=b'0'`，不用 status（现库 0 行停用无区分度，且停用题同样要求完整性）；
②LEFT JOIN 让"0 个 current"显式成行，不靠 NOT EXISTS 另查一路；③计数只算 `is_current=b'1'` 的行；
④预期结果=空集（审计基线 6613/6613 恰好 1 个 current）。与 audit-queries A-03 的差异：单趟连接一次输出
两类异常并保留明细列，A-03 是相关子查询+分桶。

## 附加 B：结构化内容块 vs raw 整段 HTML（架构权衡题参考答案）

这是"讲架构演进"的模板题，答法分四段：**当初为什么 → 后来为什么变 → 什么条件改回去 → 反向失效条件**。

- **当初选结构化块（D-23，2026-09-23）**：服务对象是"管理端重建+人工编辑回归"。块模型是必要基础设施：
  ①就绪语义落到块（缺图=显式"资料未就绪"，不许拿别的内容补）；②解析不得混入作答题面（没有块边界就没有可执行判据）；
  ③引用要精确到块；④简答需要小问级结构。
- **后来为什么转 raw（D-33，2026-09-30）**：①D-31 砍掉人工编辑——版本机器和块级编辑界失去服务对象，
  在"写入=批次导入"下整条机器空转；②实测语料 98% 纯文字，病根在转换层截断（TD-017）而非语料本身；
  ③图题仅约 156 道，v0 内联 HTML 渲染即可，结构化投入没有当期收益。
- **什么条件改回去（触发器）**：Phase 4 黄金集证明图题检索盲区实质影响召回/引用精度（届时 3.9 契约=升级图纸，按图重建而非重新设计）；
  恢复人工编辑；需要块级引用或小问级判分；新采集源自带可靠块边界使构建成本骤降。
- **反向失效条件（raw 方向自己怎么失败）**：出现"第二事实源"苗头——有人在 stem_html 上就地打补丁、
  派生物不可从 raw 重建——说明纪律 3 已被破坏，这不是调参，是回滚到块+版本模型的信号。
