# Requirements — AI 可观测与稳定性

> 历史恢复：本文根据提交 `7744041`、Flyway V4、现有测试和工程演进记录重建。

## 背景

Spring AI 路径缺少与 Legacy 一致的用量落库；重试原因、Prompt 版本、反馈归属和首 Token
延迟无法完整串联。同时应用缺少明确的并发、速率、熔断和供应商降级边界。

## 范围

- 为每次 Spring AI 调用生成 `requestId` 并写统一 Usage 记录；
- 记录引擎、同步/流式、会话、Prompt 版本、Token 来源、TTFT 和总延迟；
- 非流式响应和流式 SSE 返回可用于反馈关联的观察标识；
- 反馈更新同时校验 Usage ID 和当前用户；
- 分类 429、超时、连接错误、5xx、认证、请求错误、容量拒绝和熔断开启；
- 实现并发舱壁、每秒预算、有界重试、指数退避、Retry-After、熔断和供应商降级；
- 首 Token 发出后的流式调用不得自动重放；
- 调度和熔断事件写 Micrometer 指标。

## 非目标

- 不把供应商缺失的 Usage 伪装成准确账单；
- 不对认证、参数错误和本地容量拒绝盲目重试；
- 不在流式输出已经开始后重试完整请求；
- 当前不实现多实例共享的全局配额和熔断状态。

## 关键决策

- 稳定性策略位于应用 AI 边界，并关闭 SDK 隐式重试以避免放大；
- Legacy 保留原日志，Spring AI 观察器不重复记录同一次 Legacy 调用；
- 只有可恢复的瞬时故障重试，且次数、等待和总预算有上限；
- 主供应商失败后按配置优先级尝试备用供应商；
- 日志与反馈以服务端用户身份约束，不能信任前端声明用户。

## 完成定义

一条请求能够关联用户、会话、引擎、Prompt、Usage、延迟、反馈和错误；可恢复故障受到有界
治理，不可恢复故障快速失败；流式响应不产生重复正文。
