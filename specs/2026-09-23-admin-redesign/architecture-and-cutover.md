## 1. 技术选择（ADM-10；A-02 完整说明）

### 1.1 选择与理由

**新管理端 = Vue 3 + Vite 6 + TypeScript(可选,见 1.4) + Element Plus + Pinia + Vue Router + Axios；
工程位于新目录 `apps/frontend/admin-next`，与旧端并行开发、独立构建。**

| 维度 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3 | 学生端与管理端均为 Vue 3（tech-stack 前端基线），团队既有经验；无跨框架迁移成本 |
| 构建 | Vite 6 | 与学生端对齐（学生端已 Vite 6，旧管理端 Vite 5）；共享同一套插件与代理约定（`/api → :8003`） |
| UI 库 | Element Plus | 两个前端均在使用；管理端交互密度高，EP 的表格/表单/弹窗体系匹配；**不换 UI 库**（候选 C 否决理由见 1.2） |
| 状态 | Pinia | 两端一致的既选 |
| 路由 | Vue Router 4 | 同上 |
| HTTP | Axios | 沿用；但重写封装层（见 1.4 §API client） |
| 图表 | ECharts | 旧端/学生端已用；仅工作台一处消费，若首版砍图表则可暂不引入（依赖最小化） |
| 语言 | JS（ESM） | 与学生端一致（学生端为 JS）；不引入 TypeScript 作为首版前提——理由：单人项目优先减少构建链复杂度；目录与模块划分已按可后期渐进迁移 TS 设计。**此为默认，实施 Feature 可复核一次** |

### 1.2 备选方案与否决理由

| 候选 | 内容 | 否决/接受理由 |
| --- | --- | --- |
| A **新目录并行**（采纳） | `apps/frontend/admin-next` 新工程；旧端冻结为回归基线 | 旧端始终可运行可回退（ADM-11 前提）；新旧互不阻塞；代价：短期两套工程共存（冻结侧不新增功能，维护成本≈0） |
| B 原地替换 | 重写 `apps/frontend/admin/src` | 否决：失去可运行回退基线，切换失败无退路；违背"重建期间保留旧管理端作为行为、接口和回归基线"（路线图已确认方向） |
| C 新 UI 框架（Naive UI / AntD Vue） | 换库重设计 | 否决：无独立需求驱动（requirements"不为版本对齐顺手升级"同源约束）；新增依赖学习与移除成本；与学生端 UI 分叉；视觉基线由 A-03 的布局/间距/状态规范承担，不靠换库 |
| D 微前端（qiankun 等） | 新旧同壳混跑 | 否决：引入新框架与运行时复杂度，无独立扩缩容/团队边界需求（tech-stack 条件式扩展原则） |

### 1.3 依赖影响（不为版本对齐顺手升级）

- **新增**：仅基线六件（vue/vite/element-plus/pinia/vue-router/axios），全部使用与学生端相同主版本线；
  ECharts 按需。每项在实施 Feature 的 package.json 变更说明中登记"解决的问题/备选/移除成本"。
- **不继承**旧端 12 个未使用依赖（codemirror/jsonlint/dropzone/file-saver/jszip/xlsx/fuse.js/
  screenfull/driver.js/clipboard/vue-count-to/path-to-regexp 等 vue-element-admin 遗留）。
- **不升级**学生端与后端的任何版本（本 Feature 范围外）。
- 旧端依赖**不清理**（冻结原则：少动为安）；其安全升级仍在 TD-011 处理。

### 1.4 工程结构与模块边界

```text
apps/frontend/admin-next/
├─ src/
│  ├─ api/            # 按域一个文件（auth/questions/papers/answers/ai/system…），
│  │                  # 全部经 request.js：响应/HTTP 双层错误、401 单例跳转、requestId 透出
│  ├─ stores/         # auth(内存态用户)、dict(学科/题型/状态枚举——以后端枚举为准，不硬编码 3/4 语义)
│  ├─ router/         # 四区静态路由 + 登录守卫（仅"是否登录"判断，不做角色分支）
│  ├─ layout/         # 顶栏+侧边+内容区；无旧端死代码
│  ├─ views/          # 与 P1~P16 一一对应（content/exam/ai/system/workbench 分目录）
│  ├─ components/     # QuestionPreview（data-src 内联规则）、StatusMatrix(四维状态)、
│  │                  # BlockEditor(块编辑)、ConfirmLevels(L1~L3)、PageList 三态封装
│  └─ styles/         # 布局/间距/状态色规范（视觉基线，A-03）
└─ vite.config.js     # base=/admin-next/（生产），dev :8002，/api 代理 :8003
```

**复用边界**：

- **不复制**旧端任何 layout/components 死代码；
- `QuestionPreview` 的 `data-src → fetch 内联 → data-fallback` 语义按现行展示事实**重写**
  （资产 URL 规则与旧端一致：`question-html/… → /student/…`），不 import 旧端代码；
- 与学生端**不合并工程**（tech-stack 约束），仅共享视觉与交互规范；
- 后端 API 语义一律以 `api-contract.md` 为准，前端不定义业务事实（题目/版本/就绪/停用语义均来自后端字段）。

## 3. 部署形态与切换设计（A-05）

### 3.1 部署形态

- 新端构建产物部署为独立静态目录，经反代以 `/admin-next/` 提供访问；
  后端 `/api/admin/**` 完全不变（新旧共享）。
- 切换 = 反代把管理端入口（原 `/admin/`）指向新产物；旧产物目录保留原位不删。
- 与 `2026-09-23-public-deploy` 的关系：部署产物、反代配置、健康检查归该 Feature 的发布流程；
  本文件定义**管理端切换的判定与步骤**，两者在实施时合并执行。

### 3.2 发布前核对清单（全部满足才允许切换）

| # | 核对项 | 证据形式 |
| --- | --- | --- |
| 1 | DB-1~DB-7 已落地且 9.20 迁移对账通过（引用其验收，不重设阈值——D-11） | 9.20 实施 Feature 验收记录 |
| 2 | BE-1~BE-2 完成；`api-contract.md` 六个示例场景（冲突/重复提交/过期/缺资源/索引失败/分页）接口级验证通过 | 接口测试记录 |
| 3 | 旧端消费的改造端点字段全部向后兼容；旧端主流程回归通过（登录/题库/试卷/AI 三页） | 旧端回归清单 |
| 4 | 新端 validation 场景 1~7 在联调环境走查通过 | 走查记录 |
| 5 | 双端登录隔离在新端复验（AUTH-01~06 回归） | 复用 9.21 验证脚本/测试 |
| 6 | 回滚步骤演练一次（反代切回旧产物可行） | 演练记录 |
| 7 | 待新增页面无"伪装可用按钮"（对照 F-11 红线与矩阵 [待新增] 状态） | 走查记录 |

### 3.3 旧入口冻结规则

- 自本设计定稿起，旧管理端进入冻结：**仅修复阻断性缺陷**（无法登录、数据损坏级），
  不新增功能、不做优化性重构；缺陷修复须在新端同步体现或评估是否仍需要。
- 冻结范围含其 `dist`（不再重发布，除非阻断修复）。

### 3.4 整体切换步骤与回滚

**切换**（可在一个维护窗口内完成，预计 <30 分钟）：

1. 确认 §3.2 清单全绿；备份当前反代配置。
2. 反代 `/admin/`（管理端入口）→ 新产物；`/student/`、`/api/**` 不动。
3. 冒烟：新端登录 → 工作台待办 → 题目列表 → 打开一道题预览；学生端登录冒烟不受影响。
4. 观察 24h：后端错误日志（5xx/requestId）、双端登录事件、编辑保存成功率。

**回滚**（任一步骤失败或观察期出现 P1 级问题）：

1. 反代 `/admin/` 指回旧产物（一条配置变更 + reload）。
2. 新端入口（`/admin-next/`）保留但置"维护中"页，**停止新端写操作**。
3. 数据不回滚：新旧共享同一后端与数据库，新端切换期间产生的题目版本、试卷、待办状态
   全部为后端数据，旧端按其现有读路径消费；新端新增的**读侧字段**（就绪列、版本号）旧端不读，无影响。
4. 若问题源于改造端点（BE-1）的兼容性破坏：回滚该端点版本（后端发布粒度回退），而非回滚数据库。

### 3.5 回退窗口

- 旧产物保留 **≥14 个工作日**（覆盖一个完整出题/考试周期）；
- 窗口内每周复核一次"新端阻断问题清单"，归零后进入退役评估（§4）；
- 窗口结束后旧产物归档（tag + 构建物存档），反代与静态目录移除。

## 4. 退役条件（三条分开，不用永久兼容替代退役）

### 4.1 旧管理端前端（`apps/frontend/admin`）

**删除条件（全部满足）**：

1. 切换完成且 §3.5 回退窗口结束；
2. 新端 16 页上线且无 P1 缺陷；
3. 仓库 README/specs/roadmap 中对旧端的所有引用已更新为"已退役（tag 归档）"。

处置：目录删除，git tag `admin-legacy-retired` 归档；`public/admin/**` 静态副本随目录移除。

### 4.2 旧接口（逐组，条件独立评估）

| 接口组 | 退役条件 | 备注 |
| --- | --- | --- |
| `POST /api/admin/question/delete/{id}` | 新端停用流程上线 + 旧端退役后；历史软删数据保留（语义并入 `status` 的展示） | 冻结期不再被新端调用 |
| `POST /api/admin/question/upload`、`/upload/txt` | 转换器（v1→canonical）+ 事务修复落地，且确认无外部调用者后重新评估；**退役前保持冻结** | TD 写入口五处之一 |

| `/api/user/login` 与 `/api/user/logout`（旧共享入口） | **引用 9.21 遗留项**：需先盘点非 Web 调用者并定义清理与重新登录策略（roadmap 已登记）；不在本 Feature 决定 | 与新管理端无调用关系 |
| 其余 `/api/admin/**` 既有端点 | **不退役**：新端继续消费（契约兼容） | — |

### 4.3 旧表（题目域）

**全部引用 9.20，不另立标准**：

- `t_text_content` 题目部分：按 D-27 分字段退役（R-1～R-4 满足后"停写→切读→确认→观察"），整表保留；
- `t_question` 重复内容列：读侧本已不可达，随 R-1～R-2 切换进入退役清单；
- `t_essay_question`：休眠不复用（物理设计 §10 U-11 结论），无退役动作；
- `question_asset`：候选 9 启用后**结束休眠**（反向：从退役对象变为资源契约载体）。

## 5. 切换推演（validation ADM-11 三场景）

| 推演 | 过程 | 结论 |
| --- | --- | --- |
| ① 新后端未就绪 | 假设切换日 BE-2 的 rag status 未完成：RAG 状态页不上线（不在导航出现），工作台待办中"RAG 缺口"条目按 F-11 红线显示说明文字而非假按钮；其余页面不受影响（依赖矩阵按页隔离） | 切换可部分进行；就绪依赖按页面隔离，无全局阻塞 |
| ② 切换后新增题目 | 管理员在新端创建题目 v1（写 `question_content` v1 + 双写兼容表示）→ 切换失败回滚到旧端：旧端列表读旧 JSON 短标题、编辑回显旧 JSON 选项——**该题数据完整可编辑**（双写未取消）；若已进入 9.20 读切换后期（旧 JSON 停写）则**禁止回滚到旧端做编辑**，只允许只读回退——此约束写入 §3.4 回滚步骤 3 的执行前提 | 回滚安全，但存在一个时间边界：兼容双写期结束（D-27 R-3 停写）后，旧端仅可作只读回退；该边界由 9.20 实施 Feature 的退役阶段宣告 |
| ③ 回滚新前端 | §3.4 步骤执行：反代回旧端、新端停写；新端切换期间产生的数据（新版本行、待办状态）保留且旧端可消费 | 不丢数据；唯一不可回退的是"已删除的旧产物"——故 §3.5 要求窗口 ≥14 工作日 |
