# 规范驱动开发（SDD）工作说明

本项目采用 DeepLearning.AI 与 JetBrains 合作课程 **Spec-Driven Development with Coding Agents** 的工作方式。
本文件是工作入口；项目目标、技术约束和排期分别见 [mission](mission.md)、[tech-stack](tech-stack.md)、[roadmap](roadmap.md)。

官方资料按提交 `4a9c2ac8cdac38a6689b65512461dde614487650` 核对。
[官方内容索引](references/sdd-course.md)提供逐项来源、提示词顺序、示例说明和本地采用方式。
本文用中文归纳与改编，不是课程逐字稿，也不把项目自定规则称为官方要求。

## 先掌握工作循环

**讨论当前问题 → 留下本轮记录 → 更新有效规格 → 实现一个可验收结果 → 验证并反馈 → 继续或重规划。**

用户只要求讨论或编写规格时，做到对应范围；已经授权实施时，在明确范围内持续执行，不逐步重复求许可。
不知道未来所有细节，不妨碍把当前小步骤做清楚；影响当前步骤的歧义先解决。
功能完成取决于约定结果、验证与作者理解，文档数量或 plan 勾选率不是替代品。

## 官方机制与项目扩展

| 机制 | 官方示例如何使用 | 本项目采用方式 |
| --- | --- | --- |
| 项目宪法 | mission、tech-stack、roadmap 建立稳定上下文 | 保留三文件及现有 Java / Spring AI 技术方向 |
| 功能规格 | 日期目录下 requirements、plan、validation | 保留三份有效规格，逐轮完善 |
| 访谈 | 编写前集中询问范围、决策、上下文 | 已有明确答案直接引用，只问真正缺失的内容 |
| 小阶段 | 优先聚焦、可独立交付的 Feature 和可独立审查任务组 | 每组说明可见结果及验证办法，发现过大就拆分 |
| 迭代修改 | 实施、验证时继续调整规格，必要时合并或重排阶段 | 修改受影响部分并保留原因，不反复扩写全系统 |
| Git | 功能分支开发，验证后提交、合并、删除已合并分支 | 分支名与提交节奏遵循下方规则及用户授权 |
| Changelog | 根据已发生提交生成按日期分组的变化说明 | 按提交范围核对，不能把讨论或待实现计划写成成果 |
| Backlog | 保存尚未实施的研究和候选方案 | 不自动排期，确定近期交付后才进入 Feature |
| 可复用工作流 | 将重复的 feature-spec 和 changelog 提示提取为 skill | 可以按需提取，不自动安装或运行官方 skill |
| 可替换代理 | 通过规格、代码和材料让工作可以接续 | 交接当前版本、未决问题、授权边界和下一步 |
| 讨论记录与自我考核 | 未发现统一的完整问答归档或作者考核模板 | 作为本项目扩展，明确记录，不冒称课程规定 |

官方的 `prompts.md` 是编号提示词序列，不是完整人机聊天导出。
官方前期可以只做编译、启动与 HTTP 检查，后期才引入自动测试；按实际风险选择验证，不机械复制所有阶段的要求。
课程的大型 AgentClinic 示例与实际教学快照并非同一技术方案，不直接把其框架或业务表搬到本项目。

## 三层工作结构

### 规范效力与变更

- 用户明确指令及系统/开发者要求优先于仓库文档；规范不扩大代码、数据库、部署或外部写操作的授权。
- 目标与非目标以 mission 为准，技术边界以 tech-stack 为准，当前排期以 roadmap 为准。
- 本文件规定工作方式；Feature 在上述边界内明确范围、决策、实施和验收。
- 事实纠正文档中的现状；事实本身不自动授权改变产品目标、技术边界或线上数据。
- 同层规范冲突时说明冲突及影响，结合最新明确指令修正；不能在代码里暗中选一个方案。
- 已确认决定不重复盘问。调整实质范围或用户保留的关键选择时，先说明具体影响再继续依赖它的工作。
- 历史实验、讨论和旧版本不为制造一致性而重写；更正用追加说明或新一轮记录，当前有效规格相应修订。
- 本轮总工作流修订由用户要求全面整理官方材料而开展；是否提交仍遵循既有约定，不自动提交。

### 1. 项目宪法

| 文件 | 内容 | 不承担的职责 |
| --- | --- | --- |
| [mission.md](mission.md) | 产品为什么存在、服务谁、成功标准、作者学习目标 | 不冒充当前全部能力已实现 |
| [tech-stack.md](tech-stack.md) | 当前技术事实、选择理由、依赖与架构约束、测试方式 | 不因课程用 TypeScript 就改仓库运行基线 |
| [roadmap.md](roadmap.md) | 当前主线、阶段依赖、范围去向与进展 | 不把所有想法直接排成必须完成的任务 |

开始新功能先读三份文件，再读相关实现和已有证据。资料已有答案时直接沿用。
从空项目开始时先访谈产品意图；维护成熟项目时先核对运行事实与当前边界。
宪法应足以帮助决策，不堆放每轮聊天、实验原文或页面细节。

### 2. 功能规格

目录结构与命名统一如下，既有目录不为新命名偏好搬动：

```text
specs/
├─ sdd.md
├─ mission.md
├─ tech-stack.md
├─ roadmap.md
├─ references/sdd-course.md
├─ templates/
│  ├─ requirements.md
│  ├─ plan.md
│  ├─ validation.md
│  └─ discussion.md
└─ YYYY-MM-DD-feature-name/
   ├─ requirements.md
   ├─ plan.md
   ├─ validation.md
   ├─ discussion.md
   └─ evidence/             # 有真实证据需要保存时再建

backlog/                    # 仓库根目录，按需创建研究条目
CHANGELOG.md                # 仓库根目录，按需记录实际提交变化
```

新 Feature 使用建立当天日期与描述性名称，不因以后补写而改日期。
三份主规格是执行入口；有多轮讨论的活动 Feature 同时维护 discussion。
不强制所有历史 Feature 回补讨论记录，不伪造过去没有保存的原话。
本项目的 specs 根目录及 Feature 不新增 README；导航由本文件和三份主规格承担。

| 文件 | 当前用途 | 更新方式 |
| --- | --- | --- |
| requirements.md | 本期做什么、不做什么，批准决策及理由、依赖和待定问题 | 保持当前有效内容；重要变更回链讨论轮次 |
| plan.md | 有依赖顺序的编号任务组、每组结果和必要操作 | 当前步骤具体，后续可待定；失效任务移除或标替代 |
| validation.md | 如何证明本期结果，正常与失败场景、证据入口及考核 | 区分验证目标与已执行记录，不预填通过 |
| discussion.md | 用户诉求、方案、分歧、接受/否定、下一问题 | 按轮追加，保留推导过程 |
| evidence/ 或已有报告 | 命令、样本、运行结果、截图、数据与限制 | 原始事实保留，正文只链接必要结论 |

三个主规格从模板选取适用内容；不要求把所有可选栏目填满。
数据库 SQL、ER、接口矩阵和线框有实际用途再补；简单功能不复制一套大型附件结构。
roadmap 是项目级进度入口，plan 可记录任务级完成，validation 记录验证结果；任务完成不自动关闭 Feature。

### 3. 讨论、研究与历史记录

#### 逐轮记录 discussion.md

用户围绕本 Feature 进行一轮实质讨论后，在同一轮工作中追加一条记录，再同步已确认结论。
用户明确要求暂不写文件时先遵从；无法确定归属时不要给多个 Feature 各复制一份相互冲突的记录。

每轮包括：

1. 日期、轮次与主题。
2. 用户诉求：关键原话，或明确标为“意译/摘要”。
3. Agent 的建议及所依据的代码、实验或来源。
4. 结论：已接受、已否定、待决定；沉默不当作接受。
5. 本轮修改了哪些规格/任务，或为什么没有修改。
6. 当前剩余问题与下次可继续的入口。

重要分歧、改方向原因及关键措辞保留。常规工具输出用证据链接代替，不复制口令、Token、
私人数据或内部推理。讨论中的建议不会因写进日志就升级为批准决策。
新一轮推翻旧结论时，旧记录保留，新增更正并更新有效规格；不要同时执行两套相反规则。

采用 [discussion 模板](templates/discussion.md)。首次为历史功能补建时，注明“根据现有材料回顾”，
区分可见原话与事后整理，不虚构完整聊天记录。
本次 SDD 工作流编写本身的讨论见 [本次记录](references/sdd-workflow-discussion.md)。

#### Backlog

未来功能、未采纳方案和研究结果可以存入根目录 `backlog/YYYY-MM-DD-topic.md`。
内容保持简单：问题、候选、依据、代价、未决项和何时值得再看。
backlog 不是正式排期；跨入近期交付时再在 roadmap / Feature 明确采用范围。
当前讨论只需要留一两句的想法，可以先记在 discussion，不为每个想法新建文件。

#### Changelog 与 Git 历史

CHANGELOG 说明已经发生的变化，Git 保留具体版本与差异；discussion 说明思路与未提交讨论。
首次生成 Changelog 可从已确认纳入的提交整理；后续按提交范围增补，人工核对去重与措辞。
官方脚本按日期读取提交且丢弃最后记录日期，同日后续提交可能遗漏；不能照搬为精确增量审计。
本项目若需要自动化，应追踪已记录提交而非只比较日期。当前不因整理规则而新增脚本、运行历史生成或提交。

### 4. 本地模板与使用原则

- [requirements 模板](templates/requirements.md)：目标、范围、可见结果、决定、上下文。
- [plan 模板](templates/plan.md)：当前任务组、依赖、结果与操作。
- [validation 模板](templates/validation.md)：检查、人工场景、证据、完成判据及考核。
- [discussion 模板](templates/discussion.md)：每轮交流记录。

模板是辅助，已明确的内容直接写入，不用占位符替代已有结论。
起稿可以只填已明确部分，未决问题写清对当前工作的影响。实施前把当前步骤的目标、操作和验证收口，
不用预设计所有未来表、页面或测试。不适用栏目删除或注明理由，不制造填表任务。

## 从新 Feature 到交付

### 1. 选取当前最小交付

读取 roadmap 和进行中的 Feature，先判断该继续现有工作，还是确实需要新功能。
官方 skill 以“第一段全部未勾选的阶段”选下一项；本项目有进行中任务、依赖与插入项，不能仅靠复选框自动跳过。
用一句完整的话说明：谁在什么条件下，能完成什么，以什么结果结束。

优先聚焦可独立交付的范围。任务过大时按业务结果和依赖拆分，不先横向建完全部表再横向写完全部页面。
小阶段指工作足够聚焦，不承诺所有功能都能在一次聊天或固定时间内完成。

### 2. 明确范围、决策、上下文

官方 feature-spec 先集中访谈这三个方面，本项目保留问题含义：

- 范围：这次用户能完成什么？哪些行为/数据属于本期？
- 决策：哪些存储、交互、可见性、验证或实现取舍影响结果？
- 上下文：沿用什么栈、模式和语气，保护什么环境，存在哪些未决问题？

已有回答直接引用；问题按信息缺口提出，不每次重新问三遍。
可用结构化提问工具时用于收集真正影响方案的信息，不为套模板强制阻断工作。
用户要一轮轮讨论时，先处理当前问题并保存这一轮；明确范围后再逐步细化下一步。

### 3. 组织分支与规格

实现隔离优先使用合适的功能分支，默认新分支前缀为 `codex/`；已有相关分支可继续使用。
先检查当前分支及工作区，保留其他人的未提交修改，不擅自重置、覆盖或切走它们。
Git 分支、worktree、提交、推送和合并遵从本次授权与仓库约定，不因课程示例使用命令就自动执行。
用户要求“规格写完后一次性提交”时，讨论阶段保持工作区修订，不逐轮提交。

建立日期目录并完善三份规格和讨论记录。讨论文件不要求独立分支，也不自动授权实施。
当前做设计还是做实现，在 requirements 明确区分；设计交付不用假装已运行，实施不能只交文档。

### 4. 编写可执行任务组

每组写明当前要产生的结果、所需输入、涉及的操作与验证。
任务组编号，按依赖排序，具体到执行者能定位实现；以实际代码核对路径，不凭模板编造。
任务中可以复用已有数据库、服务、接口、页面和测试；说明适配点，避免重复建设。

课程反馈表单常按数据、组件、路由、导航、测试组织任务；这是其示例的实现分层，不是每个项目必须照抄的分组。
本项目按业务模块交付，模块内部再按这些技术依赖组织。
后续步骤不确定时保留简短候选与触发条件，不给它们伪造固定批次和验收数量。

### 5. 实施并同步规格

在已授权范围内推进当前任务，先利用现有模式和成熟代码。
实现发现规格遗漏、API 不存在或数据不符时，核对事实并修订受影响条目；关键范围改变再由用户决定。
技术细节已被授权且不改变范围时由执行者判断，不把常规动作都变成审批。

每轮实施反馈说明：交付了什么、怎样验证、暴露什么问题、下一步处理什么。
更新任务状态与证据引用；每轮结束追加 discussion。不要只在聊天中说“已完成”，仓库仍停在旧状态。
需求变化可从用户评论直接开始，例如修改组件边界、添加某个必要任务，然后同步相关规格。

### 6. 验证与审查

验证与本期结果匹配：可用编译、静态检查、单元/契约/集成测试、HTTP 冒烟和浏览器走查等。
新增或修改测试以真实风险为依据；低影响文档改动只做链接、结构和差异检查，不为形式制造测试。
课程早期 Hello Hono 用编译、启动、HTTP 检查验收，明确不要求自动测试；后期才按项目配置引入测试。

UI 场景检查实际渲染、交互、空态/错误态和适用的响应式/可访问性；只做接口的功能按实际结果验收。
有文案风格要求时检查用户可见用语；没有就不把课程的喜剧语气当作本项目约束。
数据库、权限、并发、副作用和 AI 能力按本项目已有技术边界验证。

记录命令、环境、代码版本、样本、真实结果、限制及未验证项。Mock、静态核对和真实运行分别标明。
实施类功能还要核对选定用户场景从输入到结果，以及适用的留存/后续使用和关键失败。
设计类功能以设计交付与推演验证，不为关闭设计而提前改生产系统。
代码审查核对需求覆盖、逻辑、兼容与维护性；只有用户或适用指令要求时才使用多代理，不照搬课程提示自动启动。

### 7. 收口、提交与合并

先核对有效 requirements、任务和验证结果是否一致，未完成项是否改变本次交付含义。
Feature 完成以约定技术验收为准（2026-10-20 起自我考核不再是完成门槛）；学习状态如实标注，不冒充掌握。
提交前说明本次涉及文件、证据与未验证部分；只提交本次范围，不夹带其他工作区修改。
按用户约定更新 Changelog、提交并合并；未获相应授权时保留可审查结果，不声称已发布。
删除功能分支仅在合并事实及清理范围明确后进行。合并不等于线上部署，发布按相关 Feature 执行。

### 8. 重规划与 MVP

完成一个阶段或遇到重大新证据后，重新看 mission、tech-stack、roadmap 及实际代码：
哪些假设仍成立，哪些功能更该先做，是否有可以缩小、拆分、合并或放入 backlog 的内容？
课程会在验证后加入测试约束、响应式要求与 Changelog，也会把多个阶段合成一个 MVP 规格。
本项目可以同样调整，但 MVP 必须有明确用户结果，不能等同于“把路线图所有内容一起做完”。

如果旧 plan 指向已否定的方向，就替换受影响计划，旧原因留在 discussion / Git 中；
仍适用的审计、测试和设计继续复用，不反复重做。
plan 已跑完而用户不认可结果时，记录未满足的目标并调整，不能用任务完成率强行关闭。

## 遗留系统接入与代理交接

### 遗留系统

先从 README、TODO、代码、现有运行环境和测试恢复使命、技术事实与当前差距。
区分继承功能、作者新增能力、设计设想和已有运行证据；代码存在不等于功能已验收。
从一个小且可验证的改动开始应用 SDD，旧系统继续作为行为和回归基线。
不把补规格变成全面重写，不用当前结构反推它天然正确，也不覆盖旧证据。

### 交接给另一位 Agent

交接至少指出：相关宪法和 Feature、当前仓库/分支/提交、工作区变更、
最近讨论轮次、已确认决定、未决问题、执行到哪里、真实验证结果及授权范围。
下一位 Agent 先读这些材料，再继续当前步骤；不因新上下文自动重开需求访谈。
原聊天没有保存的内容明确说明，不能靠“记得好像做过”认定完成。

### 重复工作流与 Skill

同一套访谈、规格或 Changelog 操作反复出现时，可以提取成可复用工作流或 skill。
官方 feature-spec 和 changelog 是参考，导入前核对适用工具、目录、语言与提交规则。
本轮只整理文档及模板，不安装全局 skill，不在仓库引入 Python 运行基线或其他无关依赖。

## 求职目标与自我考核

这是本项目在课程方式上的扩展：项目服务于作者的软件工程求职。
requirements 说明关联的面试问题来源；按问题及业务价值选技术，不为简历增加空转功能，
不用目标态文案替代工程事实。

**2026-10-20 修订（用户授权）：自我考核作为 Feature 完成门槛彻底取消。** 学习方式改为讲授优先：

- 编码代理按面经高频题直接提供学习材料：题目、参考答案、本项目事实对照与常见追问（如
  [9.20 面经讲解](2026-09-20-database-architecture/appendix/面经讲解.md)），作者自学；
- 作者可随时要求复述检查、实践验证或出题自查，也可以不做；不做不影响 Feature 完成；
- Feature 完成以技术验收为准；学习状态如实标注（已讲解 / 作者已自查 / 未学习），不冒充掌握；
- 简历表述的把关规则由[简历 Feature](2026-09-28-resume-update/requirements.md) 维护，不在本节重复；
- 历史考核记录保留有效：9.21 双端账户隔离的考核通过是真实发生的事实，不因规则取消而改写。

核心场景先区分缺实现、缺验证、仅缺表达，缺口回到对应工程范围。
课堂示例、推荐方案、发布包或测试数量均不能自动证明当前业务闭环。
