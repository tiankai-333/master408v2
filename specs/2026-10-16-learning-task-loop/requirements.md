# Requirements — 学习任务执行与多端验收

## 用户结果与候选场景

学生提出一个具体学习需求，系统能提供有依据的内容，形成练习草案；
学生确认后得到可作答试卷，交卷后能够回看保存的结果，整条任务可追踪。

候选演示：“我没弄懂进程调度，先讲解，再安排三道练习。”
具体知识点、是否同一请求内组合讲解与练习、题型与交互方式待下一轮确认，不把示例提前定死。

## 已明确方向

| 编号 | 约定 |

| D-01 | 本项建立执行 spec，以最小学习任务的实际完成为目标；本轮不授权代码、线上数据或部署操作。 |
| D-02 | 复用已有规划、事务建卷、作答和历史能力，先核对新数据链路的适配点，不重新建设考试系统。 |
| D-03 | 已有 SpringAiToolOrchestrator 使用 ToolCallingManager，显式工具执行循环上限为 4 轮。本项完善并验证任务链路及终止行为，不把已有实现说成从零新增。 |
| D-04 | 模型可以提出参数和只读工具调用；写入经身份/参数校验与用户确认。待确认状态必须与真正创建试卷区分，重复确认不得产生重复业务结果。 |
| D-05 | 数据来自 [10.13](../2026-10-13-data-admin-execution/requirements.md) 确认的读取契约，证据与引用衔接 [RAG Feature](../2026-10-16-rag-evaluation-loop/requirements.md)。用户、题目、试卷、答卷必须落在明确一致的环境，不能把新旧身份/记录默认为互通。 |
| D-06 | 新能力优先在 Web 验证完整路径；公网发布复用既有部署 Feature，微信端复用 [域名接入](../2026-09-30-wx-domain-update/requirements.md)及既有页面。具体双端功能矩阵在实施前确定，不默认重建小程序。 |
| D-07 | 保留逐轮讨论和自我考核；这次有界任务不扩展为长程自主 Agent、通用工作流平台、MCP 或多智能体。 |
| D-08 | 意图路由形态已确认（2026-10-21）：auto 自由文本默认进入既有 SpringAiToolOrchestrator 工具循环，路由由模型是否调用工具表达，澄清先以文本追问实现；前后端业务意图正则删除，规则仅保留显式 UI Command、上下文短路和安全默认。独立路由器与混淆矩阵评测不在本 Feature，评测采用端到端行为矩阵；每条 auto 文本调用一次大模型的成本随真实模型验收记录。 |

## 最小交付

1. 同一任务可追踪到意图判断、所需检索/工具、草案、确认、试卷及作答结果。
2. 当前用户可完成练习并回看结果；确认、作答与历史所依据的内容保持一致。
3. 路由澄清、资源不足、工具失败、取消/重复确认、循环耗尽有明确行为，不挂起或误写。
4. 一份可复现的任务演示记录与 Web/小程序功能矩阵，注明代码、环境和真实验证范围。

当前 loop 上限不等于已具备时间/Token预算、重复调用检测和完整 Trace；先查差距再补本场景必要部分。
只为选定任务暴露必要的工具，不为“多工具”指标拆出无意义接口。

## 第一轮要收口的问题

- 以哪条已有学习流程为核心？讲解与组卷是否合为一次请求，成功后的界面和记录是什么？
- 用户/题库/考试依赖如何复用或适配？试卷与作答的新库适配在哪一项承担？
- 哪些操作需要澄清/确认？当前步骤、时间、Token 等预算和终止提示如何确定？
- Web 与小程序各验证什么，公网采用哪个版本和环境？真实模型调用成本单独确定。

学习问题：一次工具调用与整个任务闭环有何区别？超时重试怎样避免重复建卷？为什么日志应能定位具体失败层？
