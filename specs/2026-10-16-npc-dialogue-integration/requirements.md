# Requirements — NPC 对话包接入与推理游戏闭环

## 用户结果与项目边界

开发者能按说明安装明确版本的 @wutiankai/npc-dialogue，配置角色、模型和规则，
在一个最小接入示例及 StoryCraft 推理游戏中完成多轮对话、条件判断和应用状态反馈。

包为主体，游戏为应用证据，用实际结果支撑可迁移到客服机器人的对话能力。
项目仍如实表述为 NPC/推理游戏，不虚构客服客户、工单或转人工业务。

## 最小交付

1. 代码提交、包产物与游戏引用版本的对应关系，可复现的安装/接入说明。
2. 一个小示例：提供角色知识、近期历史与当前合法条件，返回回复和候选，再由应用执行和反馈。
3. 推理游戏的一条完整交互：连续追问 → 审查候选 → 触发或拒绝 → 新状态进入后续对话。
4. 验证记录与局限：异常输出、条件未满足、模型失败、重复触发及信息提前透露分别检查。

本期不开发通用客服平台，不以包重命名替代真实改进，不强行增加 RAG/MCP/长期记忆。
历史窗口与摘要压缩不是同一能力；状态未越权也不代表回复不会泄密。

## 第一轮要收口的问题

- 哪个仓库/分支/提交是最新且应维护的版本？现有 npm 版本是否与之对应？
- 当前包与应用的真实契约是什么？先选择哪一个角色、线索和触发条件作为示例？
- 使用什么模型/替身与运行环境？需要验证现有发布包，还是先修复并形成候选包？
- 若发现回复泄密，当前最小修复与不支持的场景是什么？不先承诺“完全防注入”。

学习问题：为什么需要独立成包？上下文、模型回复、候选事件和业务状态各由谁负责？如何证明别人能接入？
