- [ ] 比较检索质量、回答引用和端到端任务成功率；
- [ ] 比较 TTFT、总延迟、吞吐、Token、成本与错误率；
- [ ] 注入 429、5xx、超时、Qdrant/Redis 故障并记录两代系统行为；
- [ ] 比较 Provider 切换、回滚、部署时间和修改影响面；
- [ ] 对不能公平比较的能力明确标记 N/A，不补造数字。

**完成条件：** 报告可复现、包含原始数据和限制；结论区分“迁移带来的变化”和“单项技术改动
带来的变化”；简历中的量化描述都能追溯到报告。

## 条件式扩展，不预排期

以下能力只有触发条件成立后才建立独立功能规格：

- 网页搜索：确有时效性问题或本地知识不足，并能完成 SSRF、Prompt Injection 和引用治理；
- MCP：至少有真实跨进程复用、外部 AI 客户端或动态发现需求；
- 多智能体：单 Agent/确定性 Workflow 已被指标证明存在上下文隔离或并行瓶颈；
- 微服务：出现独立扩缩容、故障隔离、部署边界或团队所有权要求；
- 动态 Tool 平台：静态注册已经不能满足真实产品需求，并具备版本、权限和审计设计。

这些名词本身不是立项理由。

## 能力对照

各 Phase 对作者能力的覆盖关系以 [mission 学习目标与能力模型](mission.md#学习目标与能力模型)
为准。能力差距只在 mission 中记录，不因对照存在而自动排期；任何差距项进入实施，
仍以[条件式扩展](#条件式扩展不预排期)的触发条件为唯一入口。

## 功能阶段的统一验收门槛

每个阶段在合并前至少满足：

1. `requirements.md` 中的范围、非目标和决策已确认；
2. `plan.md` 的任务组完成或明确记录偏差；
3. `validation.md` 中的自动化与人工验证已经执行；
4. 新数据库和 API 变化有兼容及回滚说明；
5. 新 AI 能力有基线、数据集、质量、延迟、成本和失败结果；
6. 文档区分已实现、已验证、未完成和条件式计划；
7. 结果同步回项目宪法、技术债和工程演进记录；
8. 作者完成并通过该 Feature 的自我考核，记录独立解释、变式追问和实践证据。

功能整体完成须同时满足技术验收与自我考核。技术完成但尚未掌握时，单独标记“待自我考核”
或“待补学复测”。上面的已有基线勾选仅表示历史技术状态，不表示作者已通过自我考核。
