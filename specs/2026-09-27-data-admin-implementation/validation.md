## 三种验收分别记录

| 验收 | 判断什么 | 不能被什么替代 |
| --- | --- | --- |
| 设计接受 | 用户看过 ER、复用范围、题目落库样例和管理流程，明确接受首版边界 | 审计跑完、旧决策逐条确认、AI 宣称设计完成 |
| 技术与使用验收 | SQL、新库、API 和新管理端满足首版操作且可复现，用户能完成操作 | 只有文档、SQL 文件、mock 页面或单模块演示 |
| 自我考核 | 作者能够独立解释、追问和实践，经作者确认结论 | AI 写出的答案或测试通过数字 |

设计确认须指向用户明确反馈及对应规格版本，不能由代理自行填“通过”。

小样本结果不外推到全量容量或所有恢复场景。

## 首个模块验收故事

授权采集结果或原创夹具 → 校验发现缺失项 → 修正采集输入/规则 → 人工确认 → 写入新库
→ 管理端列表与完整预览 → 查看来源、批次和失败原因 → 重复提交无重复题。
再执行同源内容变更，核对身份、引用与派生是否符合接受的策略。

这只证明题库闭环可用。后续按首版范围补试卷、治理与消费者验收，不冒充整个管理端完成。

## 自我考核

1. 指着 ER 解释：为什么保留这些表？哪些复用、哪些新建？数据库约束和应用校验各管什么？
2. 从一题追踪采集、入库、页面和检索：哪份是事实，哪些可重建？为什么现在不做完整版本/内容块系统？
3. 同一请求再发一次，与同一题内容发生变化有什么区别？怎样证明失败重试不多写、不漏写？
4. 没有版本表如何保护历史？题目或图片后来改变，哪些证据仍能复现，哪些不能？
5. 实践：独立在隔离环境复现建库与一批导入，定位失败项并安全重试，说明旧库为何不受影响。

先作者作答再反馈；记录日期、题目、摘要、实践、提示、薄弱点和复测。
口述不照抄答案，实践允许查代码/官方文档；核心结论正确、能说明证据、完成实践且应对变式追问才通过。
