# Requirements — 管理端与学生端账户冲突

状态：**已完成（2026-09-21）**。方案已确认并实施；自动化、HTTP 集成、真实浏览器与构建验证通过；
作者自我考核通过（作者确认）。仍未验证项：跨用户数据归属越权、部署环境（AUTH-07）；
"退出隔离/401 归属"两项自我考核为作者确认、未附输出。
证据见 [reproduction-baseline.md](reproduction-baseline.md) 与 validation.md 运行记录。

## 背景与目标

用户确认只修复双端不能同时登录的重要缺陷：同一浏览器中，学生端与管理端分别登录不同
账户时，后登录的一端不得替换或挤掉另一端的身份。保留既有账户、角色和后端权限校验。
本 Feature 独立于管理端整体重建与题目数据库设计。

## 已确认范围与代码事实

- 本地学生端使用 localhost:8001，管理端使用 localhost:8002，后端使用 localhost:8003。
- 两端 `src/api/login.js` 均调用 `/api/user/login` 和 `/api/user/logout`；请求工具携带凭据。
- `RestLoginAuthenticationFilter` 匹配同一个登录 URL；`SecurityConfigurer` 使用一套安全链、
  会话认证上下文及 remember-me 配置，退出配置为使整个 HttpSession 失效。
- `/api/admin/**` 与 `/api/student/**` 已有对应角色校验；本轮保留，不扩展权限体系。
- 上述为静态代码事实；实际 Cookie、身份覆盖时序和冲突基线仍需运行复现。
  共用登录 URL 是线索，不把“换两个 URL”当作会话隔离已成立的证明。
- [TD-001](../../docs/technical-debt.md#td-001学生端与管理端的身份角色和界面入口耦合)
  的统一身份权限治理属于更大范围，本 Feature 仅处理其中双端登录共存问题。

代码入口：`apps/backend/backend-app/src/main/java/com/mindskip/xzs/configuration/spring/security/`，
以及两端 `src/api/login.js`、`src/utils/request.js`。

## 行为契约

以下作为本次实现与验收的目标。当前端退出和过期仅作用当前端，是双端独立登录的规格默认行为。

- AUTH-01：同浏览器学生 S 与管理员 A 可同时登录，两种登录顺序均成立；页面及后端身份各自正确。
- AUTH-02：一端登录、切换账户、登录失败、退出或认证过期均不改变另一端的有效身份。
  刷新和重新打开标签页按各端自身有效凭据恢复；同端多标签页不承诺不同账户同时在线。
- AUTH-03：后端强制验证角色和数据归属，不能只依靠前端路由或菜单隔离。
- AUTH-04：保留既有账户、角色及学习记录，不以删用户、重置密码或清库解决冲突。
- AUTH-05：保留现有 remember-me 用户能力，但其凭据与退出清理不能跨端串用；不新增永久登录机制。
- AUTH-06：修复覆盖真实业务请求与身份恢复，不只修复登录响应或用户名显示。
- AUTH-07：本地双端代理环境必须验证；检查仓库现有部署路径配置，记录未验证的部署环境，
  不用切换浏览器、无痕窗口或 localhost/127.0.0.1 混用作为修复手段。

## 已确认技术决策与影响范围（2026-09-21）

复现证据见 [reproduction-baseline.md](reproduction-baseline.md)：两端共享同一 `JSESSIONID` 与
`remember-me` Cookie，第二次登录复用同一个 `HttpSession` 并覆盖其中的身份。据此确认采用：

- **同一会话内按端分区认证上下文**：会话仍是一个，但分别保存学生端与管理端的
  `SecurityContext`（`ClientScopedSecurityContextRepository`），请求按自身路径前缀
  （`/api/student/**`、`/api/admin/**`）选择读取哪一份上下文。
- **端专属入口**：新增 `/api/student/login`、`/api/admin/login` 与
  `/api/student/logout`、`/api/admin/logout`；端标识只用于选择上下文，角色仍来自账户本身，
  `/api/admin/**`、`/api/student/**` 的角色校验不变。
  端专属入口**不是隔离的前提条件**：真正起作用的是服务端按端分区存储身份、单端退出只清本端、
  remember-me 凭据按端命名。保留的旧入口按登录后的角色落盘，实测同样可实现双端共存；
  端专属入口的价值是让"这是哪一端"由客户端显式声明，而不是靠角色推断（多角色规则仍未定，见 TD-001）。
- **凭据按端隔离**：remember-me Cookie 改为 `remember-me-student` 与 `remember-me-admin`，
  一端的凭据不能在另一端被接受。
- **退出按端清理**：不再使整个 `HttpSession` 失效，只清除发起退出的那一端上下文与该端凭据。
- **影响范围**：后端认证入口、会话仓储、remember-me、退出处理；双端 `src/api/login.js`。
  **无数据库结构变更、无账户/角色/学习记录变更、无新增依赖、无新增服务。**
- **旧公共入口兼容**：`/api/user/login` 仍可用，登录成功后的身份按其角色写入对应端分区，因此
  旧调用者在其角色对应的端上继续工作；`/api/user/logout` 保留原整体退出语义，会清除本会话的
  全部端上下文与全部端 remember-me 凭据（旧入口无法知道自己属于哪一端，保留整体退出比“退不掉”
  更安全）。
- **旧凭据策略**：旧共享 `remember-me` 凭据不再用于两个端的路径；持有旧凭据的客户端在会话过期
  后需要重新登录。发布时旧登录态失效属于已说明的允许范围。
- **边界行为**：某端分区为空时，该端路径的请求按未登录处理（`401`），而不是“已登录但角色不符”
  （原实现会返回 `502`）。这是失败关闭的默认，不授予任何权限。
- **回滚方式**：前端与后端必须配套回滚；回滚后清理本次新增凭据
  （`remember-me-student`、`remember-me-admin` 及会话内的端分区属性）并重新登录。不涉及数据回滚。

## 非目标与约束

本轮仅完成 spec，不修改实现。实施时优先复用 Spring Security 和现有账户表，限定改动于
认证入口、会话/凭据隔离、退出及双端请求和状态处理。端标识只选择认证上下文，不能授予角色。

不做复杂 RBAC、权限配置页面、多角色聚合、统一工作台、SSO、前端合并或数据库账户拆分；
不引入 JWT、新服务或新依赖作为默认方案，不重建整个安全体系。

允许发布时使旧登录态失效并要求重新登录，但必须说明，不能影响账户数据。
旧公共登录/退出入口的调用者需先盘点：双端切换后不得静默混用旧共享凭据；其他调用者的兼容
策略必须明确。回滚应同时恢复配套前后端，并清理本次新增认证凭据，重新登录。

## 学习目标与完整问题

- 两个前端使用同一个后端，为什么登录状态可能相互影响？如何定位状态在哪一层被共享？
- 身份认证与权限校验分别解决什么问题？为什么页面显示正确不等于授权正确？
- 怎样证明修复既支持约定的双端登录行为，又不会让学生获得管理权限？

以上是项目自拟考核方向，不标为有面经来源的高频题。
