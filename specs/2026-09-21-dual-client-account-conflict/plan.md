## 3. 方案确认与实现

- [x] 复现后优先评估按 API 端划分认证上下文的最小方案；比较独立会话凭据与同会话分区存储认证上下文的复杂度，选择一种并记录原因，不同时实现两套。
      （选同会话分区：Servlet 只有一个会话 Cookie 名，独立会话凭据需自定义会话解析或引入 spring-session，
      成本与风险更高；决策记录见 requirements“已确认技术决策与影响范围”）
- [x] 明确登录、业务请求、remember-me 恢复、身份查询与退出使用同一端上下文；
      若新增 `/api/admin/login`、`/api/student/login` 等入口，须明确安全链匹配顺序和精确放行范围。
- [x] 核对会话 ID 轮换、退出失效和 remember-me 清理对另一端的影响；
      不以不同前端端口或不同登录 URL 作为隔离保证，不因端标识放宽角色验证。
- [x] 盘点旧公共入口及非 Web 调用者，记录兼容、旧 Cookie 清理和重新登录策略。
      （仓库内旧入口调用者只有两个前端；小程序走 `/api/wx/**` 自有 token 拦截器；兼容策略见 requirements）
- [x] 将决策写回 requirements，并明确影响范围、兼容和回滚方式。
- [x] 先增加能够复现问题的测试，再实施限定范围的修复。
      （`DualClientLoginIsolationTest` 实施前 7/7 失败，实施后 7/7 通过）
- [x] 更新双端登录/退出调用、凭据携带、用户缓存与未登录跳转，回归普通请求和流式请求。
      （两端 `src/api/login.js` 改用端专属入口；`withCredentials`、未登录跳转与前端 Cookie 名保持原样，
      因为两个前端的展示缓存键本就不同，真正共享的是会话与 remember-me 凭据）
- [x] 无数据库结构变更为默认方案；如确需超出该边界，先更新规格并说明理由。
