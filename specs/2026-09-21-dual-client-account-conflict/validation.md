## 验证场景

使用学生测试账户 S 与管理员测试账户 A；同一浏览器、同一主机名和共享 Cookie 容器进行测试。
不能只用两个独立测试客户端证明共存。以下预期来自 requirements 的双端独立契约。

| 场景 | 核对内容 |
| --- | --- |
| AUTH-01：S 登录学生端，再由 A 登录管理端；反向重复 | 双端身份查询和至少一个只读业务请求分别保持 S/A，刷新后仍成立 |
| AUTH-02/06：双端刷新与重新打开页面 | 有效身份分别恢复，页面与后端一致，不残留前一账户数据 |
| AUTH-02：当前端退出或切换账户；两端各测一次 | 当前端退出后受保护请求被拒绝，切换后为新身份；另一端身份及请求不变 |
| AUTH-02：只使一端认证过期 | 该端按现有续登策略恢复或要求登录；另一端仍有效 |
| AUTH-02：错误密码、错误角色登录 | 明确失败，不建立错误角色上下文，不改变另一端身份 |
| AUTH-05：启用 remember-me 后重新访问、退出 | 恢复各端自身账户；退出端不被旧凭据自动重新登录，另一端仍可正常恢复 |
| 学生直接请求管理接口 | 服务端拒绝未获授权的访问，不依赖前端隐藏菜单 |
| 不同用户读取学习记录和其他私有数据 | 不串号、不跨用户泄露，拒绝伪造用户标识 |
| AUTH-03：篡改端标识或错用另一端凭据 | 不能获得该凭据本身不具备的角色权限 |
| AUTH-04：修复及回滚前后 | 不修改账户、密码、角色及学习记录；只处理必要认证状态 |
| AUTH-07：本地代理与现有部署路径配置 | 真实请求使用正确认证上下文；未运行的环境显式标明 |
| 旧公共入口、旧登录态与回滚 | 行为符合记录的兼容策略；无静默串号，必要时明确要求重新登录 |

运行记录须包含日期、代码版本、环境、脱敏账户角色、操作顺序、预期与实际结果。
安全回归使用授权测试账户与无破坏性请求，不在文档中保存密码、Cookie 或 Token 值。

## 部署环境核对清单（未执行）

本地环境已按上述层次验证通过；**部署环境不能用本地的结论外推**，发布时按此清单执行。

发布顺序与兼容组合：

| 发布组合 | 结果 |
| --- | --- |
| 只发后端（前端仍旧） | 可用：旧前端仍调 `/api/user/login`，身份按其角色写入学生/管理分区，旧前端各自继续工作且两端可共存（已由集成脚本的旧入口场景验证） |
| 只发前端（后端仍旧） | 不可用（推断，未实测）：新的端专属登录入口在老后端不存在，会落到 `hasRole` 而返回 401 |
| 前后端配套发布 | 推荐：两端各自独立上下文与独立 remember-me 凭据，退出只影响本端 |

用户可见影响（发布说明必须写明）：旧登录态与旧共享 remember-me 凭据不再被读取，**所有用户需要重新登录一次**；账户、角色和学习记录不受影响。

部署环境需核对：

- 反向代理是否改写后端看到的路径（`ClientEnd.resolve` 依据 `requestURI`）；用一条探针请求确认到达后端的真实路径仍是 `/api/student/...`、`/api/admin/...`。
- HTTPS 下的会话 Cookie 属性（`Secure`、`SameSite`）与 CORS 白名单（当前为 `*` + `allowCredentials`）。
- 流式接口的代理设置（不得缓冲，参考 `v1-reference/deploy/nginx.conf` 的 `proxy_buffering off`）。
- 多实例部署时会话必须共享存储，否则端分区随之失效。

部署环境需重跑：双端共存（两种顺序）、单端退出、remember-me 恢复、服务端越权拒绝。两个验证脚本支持指向部署地址
（`-StudentBase` / `-AdminBase`；浏览器脚本用 `M408_STUDENT_BASE` / `M408_ADMIN_BASE`）。

回滚：前后端配套回滚，清理本次新增凭据（`remember-me-student` / `remember-me-admin` 与会话内端分区属性）后重新登录；无数据库结构变更，无数据回滚。

## 自我考核

先学习和验证，后独立作答；范围与通过标准在考核前确认。

1. 用本次实际证据解释两个端的账户为什么冲突，哪些最初猜测被排除了？
cookie的匹配规则不比较端口，Cookie 发送规则里，它们的主机都是 localhost。浏览器带着 JSESSIONID=abc，服务器就能找到对应的 HttpSession。一个session只有一个安全验证。排除了不同url的原因，第二次登录响应头为签发新的cookie。
2. 修复改变了哪一层的状态或规则？为什么选择这个方案，另一方案有什么代价？
SecurityConfigurer 新增 /api/student/login|logout、/api/admin/login|logout（登录入口精确放行，角色匹配顺序不变），身份从存在会话中的唯一的位置，变为按端存两个位置。退出也按端退出，不再失效整个会话。另外一个方案两个会话，收益相同但是非常复杂。
3. 如果部署方式从本地端口改成不同域名，你会重新检查什么？
检查session信息是否区分了student和admin。检查cookie是否共享。
4. 独立完成一组双端登录/退出实验，并验证一次服务端越权拒绝。
能够同时登录，退出也成功。退出后无法直接越过审核。
