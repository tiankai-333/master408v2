# 规范驱动开发（SDD）工作说明

本目录采用 DeepLearning.AI 短课 **Spec-Driven Development with Coding Agents** 中介绍的工作方式。
该课程由 DeepLearning.AI 与 JetBrains 合作推出，讲师是 JetBrains Developer Advocate
Paul Everitt。其重点不是某个特定编码工具，而是通过版本化的 Markdown 规范，让不同的
AI 编码代理都能持续、准确地理解项目意图。

> **本文件职责**：只回答"本项目如何用规格驱动开发"——工作结构、循环与分工。
> 它不承载进度状态（在 `roadmap.md`）、修订日志（在 git 提交信息）或任何 Feature 的
> 决策与验收（在各自的 requirements/plan/validation）。本文件应保持**低频变更**；
> 每次变更在提交信息中写明原因与影响。

## 核心思想

传统的 “vibe coding” 往往从一段临时提示直接进入编码，随后不断试错和修补。SDD 则先把
目标、约束、决策和成功标准写成规范，再让编码代理据此实现。规范是长期保存的事实来源，
代码代理是执行者，人始终负责范围、关键决策和最终验收。

这样做主要解决四个问题：

- 对话上下文会消失，但仓库中的规范可以跨会话保留；
- 清晰的边界可以减少代理误解需求或擅自扩大范围；
- 实现过程可以按小阶段审查、验证和调整；
- 工作流不依赖某个代理、IDE 或模型，便于更换工具继续开发。

## 三层工作结构

以下治理规则是本项目的工作约定，不声称是课程模板原文。

### 规范效力与变更

- 系统/开发者指令与用户明确授权优先于仓库规范；仓库文档不能扩大操作权限。
- 项目内目标与非目标以 `mission.md` 为准，技术边界以 `tech-stack.md` 为准，
  顺序以 `roadmap.md` 为准。Feature 只能在这些边界内细化，不能暗中覆盖它们。
- 事实与规范冲突时，事实用于纠正文档中的现状，不自动授权突破目标或安全约束。
  宪法文件相互冲突且无法兼容时，先记录冲突及影响，交由用户决定，不自行挑选方便的一条。
- 改变使命、技术边界或禁止项需要用户批准；代理可以在授权范围内整理事实和提出修订。
  每次宪法修订在 **git 提交信息**中记录日期、原因、涉及文件和影响（不单独建日志文件，
  也不在本文件保留修订表）；正文 diff 保留具体变化。
- 不覆盖旧实验结果来制造一致性；用带日期的更正说明记录新事实。修改文档不等于完成实现或验证。
- 规范应纳入 Git；是否提交遵循本次用户授权，不自动提交。未提交时明确标为工作区修订，不能冒充已版本化。
- **文档职责固定，不留发明空间**：进度与阶段状态只进 `roadmap.md`；决策只进各 Feature 的
  `requirements.md` 决策表；实验与证据只进证据文档；修订历史只进 git 提交信息。
  任何 README 只做说明与导航，不承载日志、状态或"下一动作"；**Feature 目录不设 README**，
  三份主规格即导航入口。

目录命名规则的唯一维护位置是下方“功能规格”；其他文档引用它，不再另设规则。

### 1. 项目宪法

项目首先在 `specs/` 根目录维护三个长期文档：

- `mission.md`：说明为什么建设项目、为谁服务、作者的学习目标与能力模型，以及成功意味着什么；
- `tech-stack.md`：规定技术栈、版本、架构约束和允许采用的工程方式；
- `roadmap.md`：把产品目标拆成按顺序实施的小阶段，并记录当前进展。

这三份文档构成项目的稳定上下文。开始规划任何功能前，都应先阅读它们。

### 2. 功能规格

每个功能使用独立的日期目录：

```text
specs/
├─ mission.md
├─ tech-stack.md
├─ roadmap.md
└─ YYYY-MM-DD-feature-name/
   ├─ requirements.md
   ├─ plan.md
   └─ validation.md
```

三个功能文档分别回答不同问题：

- `requirements.md`：做什么。记录范围、非目标、已确认决策、业务上下文和约束；
- `plan.md`：怎么做。将实现拆成有顺序、可独立审查的编号任务组；
- `validation.md`：怎样证明完成。列出自动化检查、人工验证、边界情况和完成定义。

开始编写这些文件前，应先与用户澄清三个方面：功能范围、关键决策、上下文与限制。
不应在需求仍有实质歧义时直接进入实现。

三问应使用具体句子：这次解决什么且明确不做什么？哪些选择必须由用户决定？
必须保护哪些已有数据、接口和运行环境？已有答案直接引用，不重复盘问。

部署类 Feature 的"运行环境"必须落到实测并写入现状事实：网络性质与可达性（含镜像供应链
每条渠道，逐项验证）、机器规格与资源上限、目标平台行为差异。"环境"不仅是目标服务器，
也包括开发机以及两者之间的传输链路。环境事实缺失是部署类规格返工的首要来源；
建立规格时应主动问询或探测，不得等实施中才暴露。

#### 可选证据文档层

复杂 Feature 可增加审计报告、入口清单、决策卡、样本契约、SQL/DDL 和测试方案，
但三份主规格仍是导航入口，不要求每个小功能复制整套目录。
requirements 维护需求与批准决策；plan 维护任务；validation 汇总验收及自我考核；
报告维护实验结果，脚本/测试代码维护实际执行行为。辅助文档链接这些事实，不复制另一套结论。
描述测试时区分“目标名称”“已存在”“已运行”；主线现状测试与候选设计测试分别标识。

### 3. 功能之间的重规划

完成并验证一个功能后，不是机械地执行旧路线图，而是重新检查：

- 已实现结果是否改变了后续假设；
- 新发现的问题应立即处理，还是加入后续阶段；
- `mission.md`、`tech-stack.md` 或 `roadmap.md` 是否需要同步更新；
- 下一阶段是否仍然足够小、可以独立交付。

小调整可以及时纳入；明显扩大的需求应进入路线图，避免当前功能不断膨胀。

## 推荐工作循环

1. 阅读项目宪法和现有代码，确定路线图中的下一阶段。
2. 为该功能建立独立分支和 `YYYY-MM-DD-feature-name/` 规格目录。
3. 先向用户确认范围、关键决策和上下文。
4. 编写并共同审查 `requirements.md`、`plan.md`、`validation.md`。
5. 在新的、干净的代理上下文中按照 `plan.md` 实现，保持任务粒度小且可审查。
6. 根据 `validation.md` 执行自动化测试和人工验证，不能只以“代码已生成”为完成。
7. 修正实现或规范之间的偏差，满足完成定义后再合并。
8. 回到项目宪法进行重规划，然后开始下一个功能循环。

## 人与编码代理的职责

人的职责：

- 提供产品意图、优先级和不可自动推断的背景；
- 回答澄清问题并批准重要技术或范围决策；
- 审查规范、实现结果和验收证据；
- 在功能之间调整路线图。

编码代理的职责：

- 阅读规范和代码库，指出缺失信息或相互矛盾之处；
- 把确认后的意图整理成可执行、可验证的文档；
- 严格依据计划进行实现，不私自增加依赖或扩大范围；
- 运行验证、报告偏差，并保持规范与实现同步。

## 遗留项目的应用方式

对于已有代码库，不应假设当前实现天然就是正确规范。可以先从 README、代码、测试、
配置和待办事项中反向整理项目宪法，再由项目负责人确认。随后选择一个范围较小的功能，
运行完整的“规格—实现—验证”循环，以渐进方式引入 SDD，而不是一次性重写系统。

## 本项目的使用约定

- `specs/` 中的文档与代码一起纳入 Git 版本管理；
- 实现前必须有明确的验证方式；
- 未经确认，不新增技术栈依赖，不突破既有安全与兼容边界；
- 规范不是一次性文档，需求或实现发生变化时必须同步更新；
- 功能完成后保留其规格目录，作为决策历史和后续维护依据。

## 求职目标与自我考核

本项目服务于作者的软件工程求职：功能选取应帮助作者理解、实践和表达可迁移的工程能力。
每个 Feature 在 requirements.md 中说明关联的完整面试问题与学习目标，在 plan.md 中安排
学习和实践，在 validation.md 中预先定义自我考核。无需为了覆盖知识点强行增加业务功能。

功能结束的标志是“技术验收通过 + 作者自我考核通过”。代码、文档或自动测试完成，不能替代
作者的理解。分别记录技术状态与掌握状态；技术已完成而考核未通过时，标为“待自我考核”
或“待补学复测”，不标记整个 Feature 完成。

默认考核包含以下内容，难度与本次实际范围匹配：

1. 独立讲述：用自己的话说明问题、方案、替代方案、取舍与验证证据。
2. 代码或设计走读：定位关键实现或设计依据，解释数据流、事务边界与失败行为。
3. 场景迁移：回答一道改变条件的追问，说明原方案是否仍适用。
4. 小实践：独立完成相关 SQL、测试、排错实验或设计推演；设计类 Feature 不强制要求实现。

考核开始前确定题目范围及通过标准。先由作者作答，编码代理再追问、反馈和讲解；考核中
不先给参考答案，不代替作者完成实践。口述与推理环节不查看现成答案；实践允许查看代码
和官方文档，所用提示如实记录。需要答案性提示才能完成的核心项，应补学后换题复测。

通过标准：核心结论无实质错误，能够说明理由和证据，能独立完成约定实践并应对条件变化。
不以背诵术语、表达流畅或 AI 给出的分数代替这些证据。

在 validation.md 记录日期、题目、作答摘要、实践证据、提示情况、薄弱点、结论和复测结果。
结论采用“未考核 / 待补学复测 / 通过”；由作者确认考核结论后更新完成状态。历史恢复的
Feature 保留原技术完成记录，自我考核状态默认为“未考核”，不得补造通过记录。

## 已恢复的历史 Feature

本项目在正式采用 SDD 之前已经实现了一批能力。以下目录根据 Git 提交、数据库迁移、测试和
工程演进记录事后恢复，用于补齐设计意图与验收证据，但不冒充当时已经存在的事前规格：

- [`2026-07-26-prompt-ops/`](2026-07-26-prompt-ops/)：Prompt 版本、审批、灰度、发布与回滚；
- [`2026-07-27-ai-evaluation/`](2026-07-27-ai-evaluation/)：固定评测集、异步运行和候选比较；
- [`2026-07-27-ai-observability-resilience/`](2026-07-27-ai-observability-resilience/)：Usage、反馈、失败分类、重试、熔断与降级；
- [`2026-07-27-hybrid-rag/`](2026-07-27-hybrid-rag/)：向量/词法融合、确定性重排和引用溯源。

每个恢复目录的文件顶部都带有“历史恢复”声明。今后新功能应在实现前创建规格，不再依赖
事后反推。
