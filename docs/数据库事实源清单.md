# Master408 数据库事实源清单

本文用于识别 Master408 每个数据领域中的权威事实、兼容数据、派生投影和索引。
第一阶段只审计“题目”领域，不修改表结构，不决定删除或合并任何表。

> **状态（2026-09-23）**：题目领域结论已经
> [`specs/2026-09-20-database-architecture/`](../specs/2026-09-20-database-architecture/requirements.md)
> 的运行期只读审计（A-01～A-13，`audit-report.md`）与隔离库设计测试（T1～T4，
> `design-test-plan.md` 第 5 节）验证；数据契约与生命周期设计已定稿
> （决策 D-13～D-28，`data-contract.md`）。**迁移与结构变更未开始**，
> 共享库结构仍为 Flyway V5 现状；`t_text_content` 题目部分的退出节奏见决策 D-27。

技术债总表见 [`technical-debt.md`](technical-debt.md)。数据库建表基线见
[`V1__baseline.sql`](../apps/backend/backend-app/src/main/resources/db/migration/V1__baseline.sql)。

## 1. 审计口径

每张表回答六个问题：

1. 谁创建它？
2. 谁写它？
3. 谁读它？
4. 它是事实还是派生数据？
5. 它与哪张表可能表达同一个概念？
6. 删除或重建它会发生什么？

本轮结论来自源码、Mapper、Flyway 和历史 SQL 的静态审计。没有通过当前数据库数据量、
孤儿记录、字段一致率和真实请求 Trace 验证的结论，统一标为“待运行验证”。

### 分类定义

| 分类 | 含义 |
| --- | --- |
| 事实源 | 业务上不可由其他数据完整恢复的权威记录 |
| 兼容事实 | 旧业务仍依赖的事实存储，未来可能迁移但当前不能删除 |
| 派生投影 | 可以从事实源重新计算或回填的数据 |
| 索引 | 为查询性能建立，可以安全重建的数据 |
| 历史版本 | 保存变更历史；当前值可能可恢复，但历史本身不可恢复 |
| 预留结构 | 表已存在，但当前运行代码没有形成完整读写闭环 |

## 2. 题目领域关系

```text
管理端新增/编辑题目
        │
        ├── t_question
        │     题目 ID、类型、科目、分值、难度、正确答案、状态
        │
        ├── t_text_content
        │     旧 QuestionObject JSON：题干、题目项、解析等
        │
        └── question_content
              新版本记录：题干、选项、答案、解析、纯文本、内容指纹

历史回填/专项导入
        ├── question_source
        ├── question_knowledge_point
        └── question_asset（目前未形成运行时读写链）

下游
        ├── 考试与答题
        ├── AI 练习规划
        ├── 知识图谱
        └── RAG 文档与 Chunk
```

当前最重要的发现是：题目内容尚未完成从旧模型到新模型的单一事实源切换。标准编辑路径
同时写三张表，读取路径则按字段混用它们。

## 4. 单表审计

### 4.1 `t_question`

#### 1. 谁创建它

- 最早来自原开源考试系统结构；
- 当前由 Flyway `V1__baseline.sql` 作为整合后的基线创建；
- 后续 408 扩展在同一张表加入了题干、来源、知识点等字段，但当前 Java `Question`
  领域对象和基础 Mapper 仍主要使用旧字段集合。

#### 2. 谁写它

- 管理端 [`QuestionController`](../apps/backend/backend-app/src/main/java/com/mindskip/xzs/controller/admin/QuestionController.java)
  调用 `QuestionService.insertFullQuestion/updateFullQuestion`；
- [`QuestionServiceImpl`](../apps/backend/backend-app/src/main/java/com/mindskip/xzs/service/impl/QuestionServiceImpl.java)
  写入题型、科目、分值、难度、正确答案、`info_text_content_id`、创建人和删除状态；
- 历史题库、专项试卷和 Demo SQL 也直接写入；
- 管理端删除采用 `deleted=true` 软删除，不是物理删除。

需要注意：管理端还存在直接调用基础 `insert` 的批量路径，是否完整维护内容表需要单独做接口级验证。

#### 3. 谁读它

- 管理端题库分页与编辑；
- 学生考试、答题记录和试卷读取；
- AI 练习规划的普通题与错题候选查询；
- 知识图谱的题目查询；
- RAG 题目文档回填；
- 多个统计和任务流程。

#### 4. 事实还是派生数据

当前应视为**题目聚合根和核心事实源**。至少题目 ID、题型、科目、分值、难度、状态和
旧业务关联由它确定。其他大量表通过 `question_id` 指向它。

但是，`title/options/correct_answer/analysis/knowledge_point/source` 等后加字段与其他表
重复，当前 Java 基础映射并未完整覆盖，不能把 `t_question` 的所有列都视为持续维护的权威值。

#### 5. 与哪些表表达相同概念

- `t_text_content`：题干、题目项、解析、部分答案；
- `question_content`：题干、选项、答案、解析及纯文本；
- `question_source`：来源、年份、题号；
- `question_knowledge_point`：结构化知识点关系；
- `question_asset`：图片和附件。

#### 6. 删除或重建会发生什么

- 不能从其他表可靠重建完整的 `t_question`；
- 物理删除会破坏试卷、答题记录、错题、知识点关系和 RAG 来源引用；
- 当前软删除只修改 `t_question.deleted`，没有看到同步禁用 `question_content`、
  `question_source`、`question_knowledge_point` 或对应 RAG 文档的逻辑；
- 因此“题目删除后是否仍能被 RAG 检索或知识图谱读取”是明确的待验证风险。

#### 当前结论

`t_question` 当前不能退役。后续设计应先把它收敛为稳定的题目身份与业务属性聚合根，
再逐步决定哪些重复内容列进入只读兼容或迁移阶段。

### 4.2 `t_text_content`

#### 1. 谁创建它

- 来自原开源考试系统，用通用文本表保存多个业务对象的 JSON/文本；
- 当前由 Flyway V1 创建，旧题库数据和多个考试对象继续引用它。

#### 2. 谁写它

- `QuestionServiceImpl.insertFullQuestion` 先写入一个 `QuestionObject` JSON；
- `QuestionServiceImpl.updateFullQuestion` 在编辑时更新同一条内容；
- 历史 SQL 和专项导入脚本直接写入；
- `TextContentMapper` 仍提供完整增删改查。

#### 3. 谁读它

- `QuestionServiceImpl.getQuestionEditRequestVM` 读取并反序列化 `QuestionObject`；
- 当前题目编辑中，题目项/选项仍主要来自该 JSON；
- 考试试卷结构、答题展示和任务等原业务也依赖不同的 `text_content_id`；
- 知识图谱的部分 SQL 直接关联；
- RAG 题目文档和 Chunk 的初始回填直接读取。

#### 4. 事实还是派生数据

对题目领域而言，它是**仍在使用的兼容事实源**，不是单纯缓存。虽然 `question_content`
已经保存结构化内容，但当前读取逻辑仍先解析 `t_text_content`，并只用新版内容覆盖部分字段。

#### 5. 与哪些表表达相同概念

- 与 `question_content.title/options/correct_answer/analysis` 重复；
- 与 `t_question` 后加的 `title/options/correct_answer/analysis` 列重复；
- 同一张通用表还保存试卷 Frame、答题文本和任务内容，因此不能把整表等同于“题目内容表”。

#### 6. 删除或重建会发生什么

- 当前不能完整删除或从 `question_content` 无损重建；
- `QuestionObject` 中的题目项、题型特定结构和旧系统 JSON 契约仍被业务使用；
- 即使题目内容完成迁移，其他考试表仍引用 `t_text_content`；
- 错误删除会导致题目展示、编辑、试卷 Frame 或答题内容无法解析。

#### 当前结论

`t_text_content` 应先按“引用它的业务类型”拆解使用范围。题目内容迁移完成不等于整张表可以删除。

### 4.3 `question_content`

#### 1. 谁创建它

- 最初由历史脚本 `12_canonical_ai_architecture.sql` 引入，目标是建立规范化、可版本化的题目内容；
- `13_backfill_canonical_ai_data.sql` 从 `t_question + t_text_content` 回填第一版；
- 当前 Flyway V1 已直接包含该结构，因此迁移编号本身看不出它晚于旧题目模型。

#### 2. 谁写它

- `QuestionContentService.backfillFromLegacy` 可以从旧表补齐缺失的版本 1；
- 标准新增和编辑题目时，`QuestionServiceImpl` 在同一事务中调用
  `QuestionContentService.saveFromEdit`；
- 每次编辑先将旧 `is_current` 清零，再插入一个递增版本的新记录。

#### 3. 谁读它

- 管理端读取题目时优先使用当前版本的题干和解析；
- 学生答题记录列表优先使用 `title_text/title` 生成摘要；
- RAG 刷新题目 Chunk 时读取当前版本的题干、答案和解析；
- 没有证据表明所有考试展示和评分路径都已经切换到该表。

#### 4. 事实还是派生数据

它具有双重性质：

- 回填得到的 `version=1` 最初是旧表的派生投影；
- 标准编辑产生的后续版本构成不可从当前快照恢复的历史事实；
- `is_current=1` 是部分新读取路径认可的当前内容，但尚未成为所有业务的唯一事实源。

因此当前判断为：**版本历史事实 + 过渡期当前内容源**。

#### 5. 与哪些表表达相同概念

- `t_text_content.content` 中的 `QuestionObject`；
- `t_question` 的内容扩展列；
- `rag_chunk.content_text` 中由当前版本生成的检索文本。

#### 6. 删除或重建会发生什么

- 可以从旧表重新生成一个“当前快照”，但不能重建历史版本和原始 `source_hash` 演进；
- 标准编辑当前同时更新旧 JSON，因此最新内容理论上存在冗余副本，但必须用数据一致性查询验证；
- 删除会使管理端和学生端失去优先读取内容，并使 RAG 的规范文本刷新无法工作；
- 若 `clearCurrent` 成功而后续插入失败，事务应回滚；该保证依赖调用始终经过事务化 Service。

#### 当前结论

暂不将它定义为完整题目事实源，也不能当作可随意重建的普通投影。下一步应验证新旧内容一致率、
版本连续性和每题唯一当前版本约束。

### 4.4 `question_source`

#### 1. 谁创建它

- 由 canonical AI architecture 阶段引入；
- 目标是把 `t_question.source/source_year/source_question_no` 和导入元数据拆成可扩展的来源记录。

#### 2. 谁写它

- 历史回填脚本根据 `t_question` 创建基础来源；
- 专项题库导入 SQL 写入更丰富的 `source_type`、URL、批次和 metadata；
- 当前 Java 运行代码没有发现对应 Mapper、Service 或管理接口。

#### 3. 谁读它

当前 Java 运行代码没有发现读取者。现有 AI 练习筛选仍使用 `t_question.source_year` 等旧列。

#### 4. 事实还是派生数据

基础的年份、题号和来源名称可从旧列派生；但 URL、页码、爬虫批次、OCR 批次和丰富 metadata
可能只存在于该表。因此它是**尚未接入业务的来源溯源事实候选载体**，不能简单视为冗余表。

#### 5. 与哪些表表达相同概念

- `t_question.source/source_year/source_question_no/tags`；
- `question_asset.source_type/source_ref`；
- `rag_document.source_type/source_name/source_ref`。

#### 6. 删除或重建会发生什么

- 从 `t_question` 只能重建基础考试来源；
- 专项导入中的 URL、批次、HTML 目录等信息可能永久丢失；
- 当前在线功能可能暂时不受影响，但未来引用溯源、版权治理和网页来源验证会失去基础。

#### 当前结论

不删除，也暂不宣布为线上事实源。先验证现有数据覆盖率、唯一性和未来来源治理需求，再决定接入读取链。

### 4.5 `question_asset`

#### 1. 谁创建它

- 由 canonical AI architecture 阶段引入；
- 设计目标是从题干 HTML 和字符串图片字段中拆分图片、公式、代码和原始文件。

#### 2. 谁写它

当前 Java 运行代码没有发现 Mapper、Service 或管理入口；历史结构和数据转储中也没有看到稳定的
自动提取闭环。

#### 3. 谁读它

当前 Java 运行代码没有发现读取者。页面仍主要通过题目 HTML 或旧图片字段展示资源。

#### 4. 事实还是派生数据

当前属于**预留结构**。如果未来只从 HTML 自动解析 URL，它可以是派生投影；如果存储原始文件、
版权来源、替代文本和排序等独有信息，它将成为不可替代的资源事实。

#### 5. 与哪些表表达相同概念

- `t_question.images`；
- `question_content.title/analysis` 中嵌入的 HTML 资源；
- `knowledge_content.asset_dir`；
- 静态文件目录和对象存储中的真实文件。

#### 6. 删除或重建会发生什么

- 表为空或仅保存可解析 URL 时可能重建；
- 如果已经存在独有的 `storage_key/alt_text/source_ref/sort_order`，则无法仅靠 HTML 完整恢复；
- 当前缺少运行数据检查，不能确认是否为空，也不能据此删表。

#### 当前结论

先保持休眠。未来启动资源治理前，应先定义“文件对象、业务引用、来源许可、删除生命周期”四个概念，
而不是直接给现有页面增加该表写入。

### 4.6 `question_knowledge_point`

#### 1. 谁创建它

- 结构在旧数据库后期已经出现；
- canonical 回填脚本通过 `t_question.knowledge_point/tags` 与 `knowledge_point.name` 精确匹配生成关系；
- 当前 Flyway V1 将其纳入基线。

#### 2. 谁写它

- 历史回填脚本；
- Demo Seed；
- `QuestionKnowledgePointMapper` 提供插入和删除方法，但当前 Java Service 中没有发现实际写调用；
- 标准题目新增和编辑流程没有同步维护知识点关系。

#### 3. 谁读它

- `KnowledgeGraphServiceImpl` 按题目和知识点读取关系；
- 学生端知识图谱、知识点详情和相关题目因此依赖它；
- AI Planner 的直接题目筛选仍主要使用 `t_question` 的旧字符串字段，而不是该关系表。

#### 4. 事实还是派生数据

当前它是**知识图谱的运行时关系读模型**。初始数据是旧字符串的派生投影，但 `relevance` 和未来人工
校准关系无法可靠从字符串恢复。由于写入闭环缺失，它还不能成为稳定的唯一事实源。

#### 5. 与哪些表表达相同概念

- `t_question.knowledge_point`；
- `t_question.tags`；
- `rag_chunk.knowledge_point_id`；
- `rag_document.knowledge_point_id`。

#### 6. 删除或重建会发生什么

- 可以通过旧字符串精确匹配重建一部分；
- 模糊匹配、人工纠正、一题多知识点和 relevance 权重无法保证恢复；
- 删除会让知识图谱无法查到题目关联；
- 新增或修改题目后不维护该表，会造成图谱逐渐陈旧，而系统目前没有显式报错。

#### 当前结论

这是当前题目领域最明显的“读取已上线、维护未闭环”问题之一。是否把它升级为权威关系表，
取决于后续是否提供可靠的标注、审核和同步流程。

## 5. 当前读取优先级

标准题目编辑读取大致采用以下顺序：

```text
题目业务属性
  → t_question

题目 JSON 与题目项
  → t_text_content

题干、解析
  → 先读 t_text_content
  → question_content.current 存在时覆盖

RAG 规范文本
  → question_content.current

知识图谱关系
  → question_knowledge_point
```

这说明当前不是严格的“双写双读”，而是**按字段分裂的混合事实源**。标准新增/编辑能够在一个事务里
同步 `t_question + t_text_content + question_content`，但来源、资源、知识点关系和 RAG 索引并不在
同一个同步边界里。

## 6. 已确认的题目数据库演进债

### DB-TD-Q01：题目内容存在三个重叠表示

- `t_text_content.QuestionObject`；
- `t_question` 后加内容列；
- `question_content` 版本化内容。

风险不是单纯浪费空间，而是字段级权威来源不同，读取者可能得到不一致答案。

### DB-TD-Q02：标准编辑的双写边界不覆盖全部题目关系

标准编辑同步旧内容和 `question_content`，但不维护：

- `question_source`；
- `question_asset`；
- `question_knowledge_point`；
- 已经进入 RAG 的文档、Chunk 与向量。

### DB-TD-Q03：软删除没有形成下游失效闭环

当前删除只标记 `t_question.deleted=true`。需要验证知识图谱、RAG、来源、资源和历史试卷应该：

- 保留但不再用于新组卷；
- 继续显示历史快照；
- 立即停止检索；
- 还是进入异步清理。

在业务语义确定前不能直接级联删除。

### DB-TD-Q04：规范化关系表缺少在线维护入口

`question_source`、`question_asset` 和 `question_knowledge_point` 已经表达了更成熟的数据模型，
但当前管理端题目生命周期没有完整维护它们。数据库设计与应用写模型尚未对齐。

### DB-TD-Q05：数据库没有强制关键关联完整性

六张表主要依赖普通索引和应用约定，没有数据库外键。现阶段不应直接补外键，必须先检查：

- 孤儿 `question_content`；
- 一个题目多个 `is_current=1`；
- 无对应题目的来源、资源和知识点关系；
- `t_question.info_text_content_id` 指向不存在内容；
- 已软删除题目仍被新试卷、图谱或 RAG 使用。

## 7. 下一轮只读数据验证

下一步不改表，先在本地数据库执行只读审计，得到以下指标：

| 指标 | 目的 |
| --- | --- |
| 六张表的总数、有效数和最近更新时间 | 判断是否仍有活跃写入 |
| 每张 `t_question` 是否存在 `t_text_content` | 验证旧主链完整性 |
| 每张有效题是否存在唯一 current `question_content` | 验证新内容覆盖率 |
| 新旧题干、答案、解析的 hash 一致率 | 判断双写是否漂移 |
| `question_source` 覆盖率及独有字段数量 | 判断它是可重建投影还是独有事实 |
| `question_asset` 实际记录数和文件可达率 | 判断是否为空壳结构 |
| `question_knowledge_point` 覆盖率和孤儿数 | 判断知识图谱完整性 |
| 软删除题目对应的 RAG/关系/来源记录数 | 确认删除泄漏范围 |

运行验证之前，不做以下决定：

- 不删除旧列或旧表；
- 不宣布 `question_content` 已经是唯一事实源；
- 不批量增加外键；
- 不建立新的双写逻辑；
- 不把 `question_source` 或 `question_asset` 接入主链；
- 不重建或清空 Qdrant 索引。

## 8. 暂定目标模型，不是迁移方案

后续如果数据验证支持，题目领域可以逐步收敛为：

```text
t_question
  → 题目身份、题型、科目、分值、难度、状态

question_content
  → 题干、选项、答案、解析及版本历史

question_source
  → 来源、年份、题号、原始页面与导入批次

question_asset
  → 图片、公式、附件及来源许可

question_knowledge_point
  → 一题多知识点、相关度与标注来源

rag_document / rag_chunk / Qdrant
  → 完全可重建的检索投影
```

`t_text_content` 是否能从题目领域退出，需要和它在试卷、答题、任务等其他领域的引用拆开判断。
这个目标只有在读路径切换、回填校验、双写观察和回滚方案具备后才能进入迁移设计。
