# Master408 技术债台账

本文用于记录 Master408 在开源考试系统基础上二次开发过程中继承和新增的技术债。
它不是“缺少热门技术清单”，也不是立即重构计划。每一项技术债都应具备代码证据、
实际影响、处理条件和可验证的完成标准。

数据库各领域的事实源与数据血缘单独维护在 [`数据库事实源清单.md`](数据库事实源清单.md)，
避免在本台账中直接根据表名推测保留或删除方案。

## 1. 使用原则

### 1.1 什么算技术债

满足以下条件之一，才进入本台账：

- 当前设计已经提高修改、测试、部署或排障成本；
- 当前实现存在正确性、安全性、可靠性或扩展性风险；
- 文档、数据模型和运行时行为不一致，容易造成错误判断；
- 为了阶段性交付主动选择了简化方案，并且已经知道其适用边界。

以下情况本身不构成技术债：

- 没有使用 MCP、Multi-Agent 或微服务；
- Tool 数量较少；
- 使用单体架构；
- 没有为了“技术先进”替换仍然满足需求的组件。

只有当缺失的能力已经造成可观察问题，或明确阻碍下一阶段目标时，才将其升级为技术债。

### 1.2 优先级

| 级别 | 含义 | 处理原则 |
| --- | --- | --- |
| P0 | 已影响数据安全、核心正确性或线上可用性 | 停止扩展功能，优先修复 |
| P1 | 持续制造行为不一致、误判或较高维护成本 | 进入近期迭代 |
| P2 | 当前可运行，但规模扩大后风险明显 | 设定触发条件，分阶段处理 |
| P3 | 体验、整洁度或长期演进问题 | 有证据和收益时处理 |

### 1.3 状态

- `待确认`：已有迹象，但还需要测试、运行数据或产品决策。
- `已确认`：代码或运行证据已经证明问题存在。
- `已接受`：明确知道风险，当前阶段决定保留。
- `处理中`：已经进入一个有验收标准的修改任务。
- `已偿还`：验收标准全部满足，并记录了验证证据。

## 3. 详细条目

### TD-001：学生端与管理端的身份、角色和界面入口耦合

- **类型**：继承债
- **优先级**：P1
- **状态**：处理中
- **代码证据**：仓库保留 `apps/frontend/student` 与 `apps/frontend/admin` 两套独立前端，分别使用
  `/student/` 和 `/admin/` 部署基路径，并维护独立的登录页面、路由和用户状态。
- **问题**：当前产品形态容易把“从哪个入口登录”与“用户是谁、拥有什么角色、允许执行什么操作”混为一体。
- **潜在影响**：多角色账号难以切换；认证逻辑重复；工作台能力按前端工程而不是权限组合；前端隐藏入口可能被误认为后端授权。
- **需要补充的证据**：确认同一账号是否允许多个角色，后端是否按角色和数据范围独立鉴权，以及两端登录会话是否可以共存。
  （“两端登录会话是否可以共存”已由 2026-09-21 的复现与修复回答：修复前同一浏览器中两端相互覆盖，
  证据见 `specs/2026-09-21-dual-client-account-conflict/reproduction-baseline.md`。）
- **已处理部分（2026-09-21）**：两端在同一浏览器中各自保持独立认证上下文与独立 remember-me 凭据，
  退出只影响本端。端标识仍由请求路径选择，只决定使用哪一份上下文，不授予任何角色；
  `/api/admin/**` 与 `/api/student/**` 的角色校验保持原样。该部分已完成技术验收与作者自我考核。
  规格与验证见 `specs/2026-09-21-dual-client-account-conflict/`。
- **仍未处理部分**：Identity / Role / Permission / Data Scope 的统一模型、多角色账号规则、
  数据范围鉴权，以及界面入口与权限组合的解耦。本条目不会因上述会话隔离工作而关闭。
- **建议方向**：先统一身份与权限模型，再决定是否合并前端。前端合并不是偿还此债的前提。
- **验收标准**：
  1. 文档明确区分 Identity、Role、Permission 和 Data Scope；
  2. 后端接口权限不依赖用户从哪个前端进入；
  3. 多角色用户拥有明确、可测试的切换或聚合规则；
  4. 权限测试覆盖越权访问，而不只验证菜单是否隐藏。

### TD-002：前后端重复承担自然语言意图识别

- **类型**：演进债
- **优先级**：P1
- **状态**：已确认
- **代码证据**：学生工作台 `knowledge-graph/index.vue` 使用“练习、组卷、出题”等正则生成
  `practice_plan`；后端 `AiIntentRouter` 又使用类似正则，并在低置信度时才进入模型 Tool 路由。
- **问题**：同一句自然语言可能被前端和后端作出不同判断；新增表达方式需要同步修改两端；显式 intent、规则 intent、上下文 intent 和模型判断的优先级不够直观。
- **潜在影响**：绕过前端调用接口时行为不同；误路由难以复现；意图评测无法对应唯一实现；模型 Tool Calling 可能在前置规则命中后根本没有机会运行。
- **建议方向**：前端只发送显式 UI 动作和上下文；自由文本由后端统一路由。后端保留高精度确定性命令，模糊自然语言进入结构化模型判断，所有结果仍由业务规则校验。
- **验收标准**：
  1. 为每种路由来源定义清晰优先级和契约；
  2. 前端不再根据自由文本正则决定业务意图；
  3. 固定意图评测集覆盖明确、模糊、否定和多意图表达；
  4. Trace 记录最终 intent、来源、置信度和是否调用模型；
  5. 前端直调与 API 直调得到一致结果。

### TD-003：Legacy 与 Spring AI 双链路长期并存

- **类型**：演进债
- **优先级**：P1
- **状态**：已确认
- **代码证据**：`application.yml` 默认 `AI_ENGINE=legacy`；Spring AI Client、Memory 和真实 Tool Calling
  通过 `ai.engine=spring` 条件装配。README 同时描述 Legacy 回退和 Spring AI 新能力。
- **问题**：不同环境可能运行不同能力集合；默认启动并不启用真实 Tool Calling；修复和测试容易只覆盖其中一条路径。
- **潜在影响**：开发、演示和面试描述与真实运行模式不一致；问题定位需要先判断引擎；两套实现持续增加修改成本。
- **建议方向**：先建立能力矩阵和迁移退出条件。完成真实环境验证后，将 Spring AI 设为主路径，Legacy 只作为有期限的回退；不要在没有回归证据时直接删除。
- **验收标准**：
  1. 文档列出两套引擎支持的功能和已知差异；
  2. 启动日志及健康接口明确暴露当前引擎；
  3. 核心契约测试对两条路径运行，或明确说明仅主路径支持；
  4. 记录 Legacy 删除条件、负责人和目标版本；
  5. 默认配置与产品主路径一致。

### TD-004：Tool、内部操作和确认命令的术语混用

- **类型**：语义债
- **优先级**：P1
- **状态**：已确认
- **代码证据**：当前只有 `plan_practice` 通过 Spring AI `@Tool` 注册；Planner Trace 中还包含
  `query_student_mistakes`、`query_questions`、`query_knowledge_graph`，但明确标记
  `realToolCall=false`；确认建卷日志使用 `compose_paper` 名称，但实际由确认接口直接调用业务服务。
- **问题**：日志或文档中的所有“工具名”容易被误解成模型可自主调用的 Tool。
- **潜在影响**：架构说明失真；Tool 成功率统计口径错误；开发者可能错误地把有副作用命令开放给模型。
- **建议方向**：统一使用 `Model Tool`、`Internal Operation`、`Confirmed Command`、
  `Skill Configuration` 和 `Trace Event` 五类术语。
- **验收标准**：
  1. API、日志、页面和文档采用一致术语；
  2. Trace 明确记录 operation type；
  3. Tool 数量只统计真正注册给模型的工具；
  4. `compose_paper` 明确保留在用户确认和后端权限边界之后。

### TD-005：AI 元数据表与实际运行时注册机制脱节

- **类型**：设计债
- **优先级**：P2
- **状态**：已确认
- **代码证据**：Flyway 基线包含 `ai_tool`、`ai_skill` 和 `ai_agent_skill`；当前源码静态审计没有发现从这些表加载并注册 Spring AI `ToolCallback` 的运行时路径。
- **问题**：数据模型表现为可配置 Agent 平台，实际 Tool 仍由 Java 注解静态注册。
- **潜在影响**：维护者可能错误认为修改数据库即可改变 Agent 能力；无效抽象增加理解和迁移成本。
- **建议方向**：先做产品决策：如果近期不需要动态注册，则把这些表标记为预留或删除未使用结构；如果确有需求，则补齐加载、版本、权限、校验、审计和失败隔离闭环。
- **验收标准**：满足以下任一方案：
  - 删除或归档未使用表，并完成数据库契约更新；或
  - 实现从配置到运行时注册的完整链路，并用集成测试证明权限和变更生效。

### TD-006：Agent 运行日志写入失败被静默忽略

- **类型**：可观测性债
- **优先级**：P1
- **状态**：已确认
- **代码证据**：`SpringAiToolOrchestrator.insertLog` 捕获 `RuntimeException` 后返回 `null`；
  `AiAgentPlannerServiceImpl.insertRunLog` 捕获 `Exception` 后同样返回 `null`，均没有记录失败原因或指标。
- **问题**：业务可以继续，但关键审计和 Tool Trace 可能无声丢失。
- **潜在影响**：线上事故无法还原；评测和成功率数据失真；安全审计存在空洞。
- **建议方向**：日志失败不应破坏只读问答主流程，但必须产生结构化错误日志和 Metric；涉及写操作的审计失败是否允许继续，需要单独制定策略。
- **验收标准**：
  1. 日志写入失败包含 request ID、异常类型和失败阶段；
  2. 增加可告警的计数指标；
  3. 测试覆盖日志库不可用场景；
  4. 明确只读操作与有副作用操作在审计失败时的不同策略。

### TD-007：Redis Memory 使用 `KEYS` 枚举会话键

- **类型**：扩展性债
- **优先级**：P2
- **状态**：已确认
- **代码证据**：`RedisStringChatMemoryRepository.findConversationIds` 使用
  `redisTemplate.keys(keyPrefix + "*")`。
- **问题**：Redis `KEYS` 会遍历匹配键空间；当前数据量小可以工作，但键数量增长后可能阻塞 Redis。
- **触发条件**：会话键达到压测定义的风险阈值、多实例共享 Redis，或 Redis 同时承担其他核心缓存职责。
- **建议方向**：使用受控 `SCAN`，或维护按用户/会话组织的索引集合；同时限制返回数量并保留 TTL 清理。
- **验收标准**：
  1. 生产路径不使用 `KEYS` 扫描会话；
  2. 大键空间压测不造成明显延迟尖峰；
  3. 会话过期后索引能够一致清理；
  4. 用户之间的 conversation ID 保持隔离。

### TD-008：限流和熔断状态局限于单应用实例

- **类型**：扩展性债
- **优先级**：P2
- **状态**：已接受
- **代码证据**：README 已明确调用预算为单实例级；当前稳定性策略使用应用内并发舱壁、速率预算和熔断状态。
- **当前决策**：单实例学习项目中，应用内治理简单且足够，不立即引入分布式协调。
- **触发条件**：部署两个及以上后端实例、供应商配额必须全局共享，或单实例策略造成实际超额调用。
- **建议方向**：优先在 API Gateway 或集中式配额服务治理；Redis 只是一种实现选择，不应仅因“已经安装 Redis”就迁移。
- **验收标准**：多实例压测下，全局并发、QPS 和熔断行为符合配置，并且单个实例退出不会永久占用配额。

### TD-009：RAG 触发范围与产品语义可能不一致

- **类型**：质量债
- **优先级**：P2
- **状态**：待确认
- **代码证据**：`AiOrchestratorServiceImpl` 当前仅在上下文类型为 `pasted_question` 时设置
  `needsRag=true`；知识点讲解、自由问答等路径不一定执行检索。
- **问题假设**：如果产品承诺“基于 408 知识库回答”，部分问题可能绕过已经实现的 Hybrid Search 和引用链路。
- **为什么尚未确认**：并非所有请求都需要 RAG；无条件检索会增加延迟、成本和无关上下文。是否为债必须由评测证明。
- **建议方向**：建立需要检索、不需要检索和检索有害三类数据集，根据任务类型或轻量路由决定是否检索。
- **验收标准**：
  1. 有检索与无检索在固定数据集上进行对照；
  2. 记录回答正确率、引用正确率、P95 延迟和成本；
  3. RAG 触发策略由指标决定，而不是由页面入口偶然决定。

### TD-010：Tool Loop 缺少重复调用指纹检测

- **类型**：可靠性债
- **优先级**：P2
- **状态**：已接受
- **代码证据**：`SpringAiToolOrchestrator` 最多执行 4 轮 Tool Loop，但没有根据
  `tool name + normalized arguments` 检测重复调用。
- **当前风险**：现阶段只有一个只读规划 Tool，最大轮数已经限制损失，因此暂不属于高优先级问题。
- **触发条件**：增加多个工具、工具成本上升、出现相同参数重复调用，或开放有副作用 Tool。
- **建议方向**：记录调用指纹、步骤预算、单工具超时和错误分类；重复调用时向模型返回结构化错误并终止或改走 fallback。
- **验收标准**：测试覆盖重复调用、超时、未知工具、非法参数和最大步骤终止，并能在 Trace 中定位终止原因。

### TD-011：前端历史依赖仍需安全升级

- **类型**：继承债
- **优先级**：P2
- **状态**：待确认
- **代码证据**：README 已将“前端历史依赖的安全升级”列为后续边界；仓库还包含从原开源考试系统迁移的编辑器、上传器和大量静态资产。
- **问题**：仅凭依赖年代不能断言存在可利用漏洞，需要以锁文件审计、实际可达路径和部署方式确认。
- **建议方向**：分别对学生端、管理端和静态第三方资产建立依赖清单；优先处理远程可利用且运行时可达的高危问题，避免无目标地整体升级。
- **验收标准**：
  1. 生成可复现的依赖安全报告；
  2. 每个高危项记录是否可达、处理方式和残余风险；
  3. 升级后完成登录、上传、富文本编辑和考试主流程回归测试。

## 4. 明确不登记为技术债的事项

### 4.1 当前没有 MCP

现阶段模型 Tool 与业务 Service 位于同一应用进程，只有一个真实 `plan_practice` Tool。
在没有跨进程复用、外部 AI 客户端接入或动态工具发现需求前，直接使用 Spring AI
Tool Calling 是更简单的选择。MCP 作为演进选项记录，不作为待偿还债务。

### 4.2 当前只有一个真实 Tool

Tool 数量不是成熟度指标。`plan_practice` 保持只读，而 `compose_paper` 位于用户确认和
后端校验之后，符合“规划与执行分离”的安全边界。只有真实用例要求时才增加工具。

### 4.3 当前采用单体架构

模块边界不清、耦合失控才是问题；单体本身不是技术债。除非独立扩缩容、团队所有权或
故障隔离需求已经出现，否则不为了微服务形式拆分。

### 4.4 当前已经使用 Redis

项目已使用普通 Redis 保存有界对话窗口，并配置 TTL。需要治理的是具体访问模式、容量、
隔离和故障策略，而不是笼统地把“缺 Redis”列入计划。

### 4.5 当前已经实现 Hybrid Search

项目已有 Qdrant 向量召回、MySQL 词法召回、加权 RRF 融合和确定性重排。后续债务应围绕
评测、触发策略、规模和效果，而不是重复建设“是否有 Hybrid Search”。

### TD-012：空库无法由 Flyway 建库，新环境不能从零初始化

- **类型**：可靠性债
- **优先级**：P1
- **状态**：已确认
- **代码或运行证据**：`apps/backend/backend-app/src/main/resources/db/migration/V1__baseline.sql:802-807`
  先对 `ai_user_key` 执行 `ALTER TABLE ... ADD COLUMN vision_model`，而建表语句在 `:809`；
  2026-09-21 在空库执行迁移得到 `ERROR 1146 (42S02) Table 'ai_user_key' doesn't exist`；
  本次设计测试因此改用"结构导出 + Flyway 历史"建立隔离库。
- **问题**：`V1__baseline.sql` 是**基线**脚本，假定库中已存在原始结构与后续迁移的表；
  从真正空的库执行必然失败。
- **实际影响**：新克隆的仓库或新环境无法用 `mvn spring-boot:run` 从零建库，
  与 `README.md` "完整数据库结构由 Flyway 管理，首次启动时会执行 V1..V5"的说法矛盾；
  任何人搭建环境都需要先拿到一份真实结构导出。
- **当前决策**：本次设计阶段不修复（属迁移/部署范围），已记入未被验证项。
- **建议方向**：把该 `ALTER` 移到对应 `CREATE TABLE` 之后；或把迁移拆成"基线（建表）+ 增量（改列）"两段；
  或在文档中明确"新环境先导入结构导出"。
- **验收标准**：在全新空库上执行 Flyway 迁移 V1..V5 全部成功，且 `DatabaseSchemaContractTest` 通过。
- **验证记录**：2026-09-21 复现 `ERROR 1146`（一次性 scratch 库，随后已删除）。

### TD-013：RAG 投影 hash 基准不一致，失效判定恒真

- **类型**：正确性债
- **优先级**：P1
- **状态**：已确认
- **代码或运行证据**：`apps/backend/backend-app/src/main/resources/mapper/RagDocumentMapper.xml:119-120`
  的刷新判据为 `rc.content_hash <> SHA2(CONCAT_WS('|', q.id, qc.source_hash), 256)`；
  同一文件的题目切片回填在 `:203` 写入的是 `SHA2(CONCAT_WS('|', q.id, tc.content), 256)`。
  两者输入不同（`question_content.source_hash` vs 旧 JSON `tc.content`），永不相等。
- **问题**：刷新语句的 `WHERE` 条件恒真。
- **实际影响**：每次刷新都会重写全部题目切片（整表写放大），而 `rag_embedding` 不随正文一起失效，
  正文与向量可能不一致；也无法用 `content_hash` 判断"是否需要刷新"。
- **当前决策**：本次设计不修复；DB-09 的投影契约已要求记录源版本与生成配置。
- **建议方向**：统一 hash 基准并把 `question_content.version` 纳入；正文刷新与向量失效同事务，
  或显式标记向量失效状态。
- **验收标准**：同一内容重复刷新 `ROW_COUNT() = 0`；内容变更后只有相关切片更新，且对应向量被标记为待重建。
- **验证记录**：2026-09-21 代码走查（`RagDocumentMapper.xml` 两处）。

### TD-014：规范内容表的选项与答案是只写字段

- **类型**：设计债
- **优先级**：P2
- **状态**：已确认
- **代码或运行证据**：隔离库测试 `QuestionVersioningTest`（T3-4）实测——把 `question_content.options`
  写成"新选项 Z"后，编辑读取路径返回的仍是旧 JSON 的"旧选项 A"；
  读取路径 `QuestionServiceImpl:175-182` 只从旧 JSON 取选项，判分 `ExamPaperAnswerServiceImpl:234`
  读 `t_question.correct`。
- **问题**：`question_content.options` 与 `correct_answer` 由 `saveFromEdit` 写入，但没有任何读者，
  字段所有权未定。
- **实际影响**：读路径切换时若不同时处理，会出现"新表有值但界面与判分仍读旧值"的静默分叉；
  也使"权威位置"无法在契约中声明。
- **当前决策**：已写入 `specs/2026-09-20-database-architecture/data-contract.md`；修复随读路径切换进行。
- **建议方向**：让读路径改读新表（推荐，与 Q-09 的结构化内容块一起做），或把这两列明确降级为投影并停止写入。
- **验收标准**：每个核心字段都能同时指出唯一权威写入者与对应读取者；契约字段表无"只写字段"。
- **验证记录**：2026-09-21 T3-4（`mvn -o test -Dtest=QuestionVersioningTest`，4/4 通过）。

### TD-015：题目资源事实在仓库之外且不在版本控制

- **类型**：继承债
- **优先级**：P1
- **状态**：已确认
- **代码或运行证据**：`apps/frontend/student/public/` 下 `question-html` 13318 个文件 / 159.1 MB、
  `question-assets` 163 / 20.1 MB、`knowledge-html` 116 / 69.3 MB、`knowledge-assets` 102 / 12.8 MB，
  四个目录均被 `.gitignore` 排除（授权原因）；
  而 `question_content.title` 的实际内容是 `<div class="question-html-ref" data-src="…" data-fallback="…">`
  外链（`audit-report.md` 第 8 节，样本 `q5-title.html` 仅 116 字节）；`question_asset` 表 0 行。
- **问题**：数据库只保存引用与降级文本，"显示事实"在仓库之外的文件里；这些文件既不进仓库，
  也没有校验值、归属或备份机制。
- **实际影响**：外部文件丢失即不可恢复；换机器或重新克隆后，复杂图文题（多图/表格/公式）
  无法还原；`question_asset` 为空会让人误以为资源已被管理。
- **当前决策**：D-19 已把资源契约纳入设计（归属、定位、校验、缺失标记、更新不得改变历史题面），
  实施阶段落地；不引入素材后台或对象存储。
- **建议方向**：以"引用 + 校验值 + 归属（题目版本/内容块）"记录资源；建立本地备份与缺失巡检；
  缺失时显式标记而不是静默降级。
- **验收标准**：任一题目版本的可达资源可列出并校验；缺失能被检出并标记；更新文件不改变历史版本题面。
- **验证记录**：2026-09-21 规模统计与样本核对（`audit-report.md` A-07/A-07b）。

### TD-016：题目领域附属表缺维护闭环与留痕

- **类型**：设计债
- **优先级**：P2
- **状态**：已确认
- **代码或运行证据**：`entry-inventory.md` 记录 `question_asset` 全仓零写入者；
  `question_knowledge_point` 的 mapper `insert`/`delete` 无 Java 调用者、运行期只读、表上无修改人/时间列；
  `audit-report.md` A-04 检出 **643 条孤儿**知识点关系（指向不存在的题目，且不是软删除残留）；
  `relevance` 的唯一写入者恒写 1.0。
- **问题**：附属表有数据但没有维护入口、没有责任人、没有变更痕迹。
- **实际影响**：孤儿关系无人处理；来源、资源、知识点的人工信息可能被回填或脚本覆盖而无从追溯。
- **当前决策**：D-20 已定"允许人工纠错、记录修改人与时间、自动任务不得覆盖人工结果"；
  本 Feature 给出候选列（`source`/`update_user`/`update_time`）与"自动不覆盖人工"的写条件。
- **建议方向**：补齐写入路径与留痕列；先隔离 643 条孤儿并查明来源；`question_asset` 要么启用要么在文档中标注为非事实源。
- **验收标准**：人工标注可写入且带留痕；自动任务带 `source <> 'manual'` 条件；孤儿关系有明确处理结论。
- **验证记录**：2026-09-21 走查与审计（`entry-inventory.md`、`audit-report.md` A-04）。

### TD-017：题干在旧 JSON 中被截断并传导到新表

- **类型**：数据债
- **优先级**：P1
- **状态**：已确认
- **代码或运行证据**：`t_text_content.id=107082`（对应 `t_question.id=8541`，2024 年 408 第 43 题）
  的 `content` 只有 677 字符，`titleContent` 长 300 字符且尾部为 `rd 000 0011 add 指令 sll`
  （在词中间断开）；`t_question.title` 与 `question_content.title` 长度同为 300、尾部完全相同
  → 截断值已传导到新表。全库旧 JSON 的键集只有
  `["analyze","titleContent","questionItemObjects"]`（6613/6613 行），没有 images 键与答案键。
  样本核对见 `specs/2026-09-20-database-architecture/appendix/sample-2024-q43.md`。
- **问题**：迁移的唯一内容输入（旧 JSON）可能本身是**截断值**，而 `backfillFromLegacy` 直接以它为源；
  现有审计（A-02）只验证了 id 链接与 JSON 合法性，**没有验证内容完整性**，因此"旧链路完整"的结论过强。
- **实际影响**：回填会把截断题干写进 `question_content`，且看起来"非空、合法"，不会被现有对账发现；
  完整内容只存在于仓库外、被 gitignore 的外部 HTML 里（见 TD-015）。
- **当前决策**：本次设计不修复；已把"内容完整性抽样"列入迁移前置条件与契约的待验证项。
- **建议方向**：以外部 HTML（渲染后的可见正文）为内容基准做一次全库抽样比对，量化截断比例；
  迁移前置校验必须包含"文本是否在词中断开/是否与外部渲染不一致"的检查。
- **验收标准**：给出截断题目的数量与清单；回填后的题干与外部渲染正文一致；对无法恢复的题目显式标记。
- **验证记录**：2026-09-21 只读 SQL 复核（`t_text_content` / `t_question` / `question_content` 三处尾部比对）。

### TD-018：`has_image` 等内容标志与事实矛盾，不可信

- **类型**：数据债
- **优先级**：P2
- **状态**：已确认
- **代码或运行证据**：`t_question.id=8541`（2024 第 43 题）实际含 **2 张图**（61 张 base64 PNG 内联在
  `q43-title.html` 的两个 draw.io SVG 中），但 `has_image=0`、`t_question.images` 为**空串**（长度 0）、
  `question_asset` 表全库 **0 行**；同类情况见于 2024 卷其它含图题（`q44-title.html` 208,650 B、
  `q47-title.html` 167,389 B，而 `q40-title.html` 仅 313 B）。
- **问题**：内容标志由导入脚本按固定规则写入，与真实富文本情况不一致；
  `has_image` 全库仅 137 行为 1，而实际含图题目明显更多。
- **实际影响**：任何以这两个标志为依据的过滤、检索提示或契约声明都会误判；
  管理端若展示"含图"标记会误导编辑者。
- **当前决策**：本次设计不修复；契约中把这两个标志标注为"不可信"，不作为强制约束。
- **建议方向**：标志要么改为由内容解析器统一生成并回填，要么在契约中降级为"提示性、非权威"；

## 7. 维护规则

- 新增债务必须附证据，避免把个人偏好写成项目结论；
- 每次只把少量 P0/P1 条目转为“处理中”，避免以全面重构代替交付；
- 偿还技术债时保留修改前后的指标、失败测试和决策理由；
